# 결정 기록

이 문서는 프로젝트에서 중요한 기술적 선택과 설계 결정을 기록한다.
모든 선택을 기록하지 않고, 이후 구현과 면접 설명에서 근거로 사용할 수 있는 결정만 남긴다.

## 001 (2026-06-02)

### Java 17과 Spring Boot 3.5.x 선택

#### 선택

Java 17과 Spring Boot 3.5.x를 사용한다.

#### 배경

프로젝트의 목표는 안정적인 백엔드 기능 구현과 성능 개선 과정을 만드는 것이다.
따라서 너무 최신 버전을 사용하는 것보다 학습 자료, 라이브러리 호환성, 실무 사용성을 고려한 안정적인 조합이 필요했다.

#### 선택 이유

- Java 17은 Spring Boot 3.x 환경에서 널리 사용되는 LTS 버전이다.
- Spring Boot 3.5.x는 최신 4.x보다 학습 자료와 생태계 호환성 측면에서 안정적이다.
- 최신 버전 적응보다 주문, 재고, 쿠폰, 성능 측정 구현에 집중할 수 있다.

#### 선택하지 않은 대안

- Java 21
- Spring Boot 4.x

#### 대안을 선택하지 않은 이유

Java 21과 Spring Boot 4.x도 사용할 수 있지만, 프로젝트 초기 목표는 최신 기능 활용이 아니라 안정적인 구현 기반을 만드는 것이다.
최신 조합은 일부 라이브러리 호환성이나 자료 부족으로 인해 구현과 학습 흐름을 방해할 수 있다고 판단했다.

#### 기대 효과

- 안정적인 개발 환경에서 핵심 도메인 구현에 집중할 수 있다.
- Spring Boot 기반 백엔드 프로젝트의 실무적인 기본기를 연습할 수 있다.

## 002 (2026-06-02)

### PostgreSQL 선택

#### 선택

주요 관계형 데이터베이스로 PostgreSQL을 사용한다.

#### 배경

이 프로젝트는 주문, 재고, 쿠폰처럼 정합성이 중요한 데이터를 다룬다.
또한 이후 성능 개선 단계에서 인덱스, 실행 계획, 트랜잭션, 락 동작을 학습하고 측정할 필요가 있다.

#### 선택 이유

- PostgreSQL은 트랜잭션, 인덱스, 실행 계획 분석을 학습하기에 적합하다.
- 주문과 재고 처리처럼 정합성이 중요한 도메인을 다루기 좋다.
- 이후 성능 개선 과정에서 DB 병목을 관찰하고 설명하기 좋다.

#### 선택하지 않은 대안

- MySQL
- 인메모리 DB 중심 개발

#### 대안을 선택하지 않은 이유

MySQL도 실무에서 널리 사용되는 좋은 선택지지만, 이번 프로젝트에서는 PostgreSQL을 통해 MVCC, 락, 실행 계획을 함께 학습하기로 했다.
인메모리 DB만 사용하면 실제 운영 DB에서 발생하는 트랜잭션과 성능 이슈를 경험하기 어렵다.

#### 기대 효과

- 주문/재고 정합성과 DB 성능 개선을 실제 DB 환경에서 다룰 수 있다.
- 이후 MySQL과의 차이를 학습하며 DB 이해도를 넓힐 수 있다.

## 003 (2026-06-02)

### Flyway와 ddl-auto validate 선택

#### 선택

DB 스키마 변경은 Flyway로 관리하고, JPA `ddl-auto`는 `validate`를 사용한다.

#### 배경

상품, 주문, 쿠폰, 재고와 관련된 테이블은 구현 과정에서 계속 변경될 수 있다.
스키마 변경 이력을 코드와 함께 관리하지 않으면 어떤 구조 변경이 언제 발생했는지 추적하기 어렵다.

#### 선택 이유

- Flyway를 사용하면 테이블 생성, 컬럼 추가, 인덱스 추가 같은 변경을 SQL 파일로 버전 관리할 수 있다.
- `ddl-auto=validate`는 JPA 엔티티와 실제 DB 스키마가 일치하는지 확인해준다.
- 성능 개선 단계에서 인덱스를 추가할 때도 변경 이력을 명확하게 남길 수 있다.

#### 선택하지 않은 대안

- JPA `ddl-auto=create`
- JPA `ddl-auto=update`
- 수동 DB 변경

#### 대안을 선택하지 않은 이유

`create`는 애플리케이션 실행 시 기존 테이블을 새로 만들 수 있어 데이터 보존에 적합하지 않다.
`update`는 편리하지만 실제 운영 환경에서 어떤 DDL이 적용되는지 명확히 관리하기 어렵다.
수동 DB 변경은 변경 이력이 코드에 남지 않아 협업과 재현성이 떨어진다.

#### 기대 효과

- DB 변경 이력을 Git으로 관리할 수 있다.
- 운영 환경을 가정한 스키마 관리 방식을 연습할 수 있다.

## 004 (2026-06-02)

### 단일 모듈 모놀리스로 시작

#### 선택

초기 구현은 단일 모듈 모놀리스 구조로 시작한다.

#### 배경

프로젝트의 첫 목표는 주문, 장바구니, 재고, 쿠폰, 결제 대기 흐름을 안정적으로 구현하는 것이다.
처음부터 MSA, Kafka, Redis 같은 인프라를 도입하면 핵심 도메인보다 인프라 복잡도가 먼저 커질 수 있다.

#### 선택 이유

- 단일 모듈은 초기 구현과 디버깅이 단순하다.
- 트랜잭션 경계를 이해하고 관리하기 쉽다.
- 성능 측정 전에는 어떤 인프라가 필요한지 판단하기 어렵다.
- 기능 구현 후 병목을 측정한 뒤 필요한 기술을 단계적으로 도입할 수 있다.

#### 선택하지 않은 대안

- MSA
- Kafka 기반 비동기 구조
- Redis를 포함한 초기 인프라 구성

#### 대안을 선택하지 않은 이유

MSA와 메시징 시스템은 운영 복잡도가 크고, 초기 프로젝트의 핵심 문제를 흐릴 수 있다.
Redis나 Kafka는 병목과 요구가 확인된 후 도입해도 늦지 않다.

#### 기대 효과

- 핵심 비즈니스 로직을 빠르게 구현하고 검증할 수 있다.
- 이후 성능 측정 결과를 바탕으로 필요한 기술을 선택하는 흐름을 만들 수 있다.

## 005 (2026-06-02)

### 주문 생성 시 재고 예약 차감 정책 선택

#### 선택

주문 생성 시 재고를 즉시 차감하고, 결제 취소 또는 결제 대기 만료 시 재고를 복구한다.

#### 배경

상품을 선택하고 결제 단계에 진입한 사용자가 결제 직전에 재고 부족을 만나는 것은 사용자 경험이 좋지 않다.
특히 티켓 예매처럼 한정된 재고를 다루는 상황에서는 결제 대기 중 재고를 예약하는 흐름이 자연스럽다.

#### 선택 이유

- 결제 단계에 진입한 사용자의 구매 가능성을 보장하는 데 유리하다.
- 결제 대기 상태와 재고 점유 상태를 명확히 연결할 수 있다.
- 결제 취소/만료 시 재고 복구 정책을 통해 정합성을 유지할 수 있다.

#### 선택하지 않은 대안

- 결제 성공 시점에만 재고 차감
- 장바구니 단계에서 재고 차감

#### 대안을 선택하지 않은 이유

결제 성공 시점에만 재고를 차감하면 결제 직전 품절이 발생할 수 있다.
장바구니 단계에서 재고를 차감하면 구매 의사가 확정되지 않은 상품까지 재고를 점유해 판매 기회를 잃을 수 있다.

#### 기대 효과

- 주문 생성 이후 결제 흐름에서 재고 정합성을 유지할 수 있다.
- 결제 대기, 취소, 만료 흐름을 실제 이커머스에 가깝게 연습할 수 있다.

## 006 (2026-06-02)

### 결제 대기 만료를 10분과 스케줄러로 처리

#### 선택

결제 대기 주문의 유효 시간을 10분으로 두고, 스케줄러가 만료된 주문을 자동 취소한다.

#### 배경

주문 생성 시 재고를 즉시 차감하기 때문에 결제가 완료되지 않은 주문이 계속 남으면 재고가 불필요하게 묶인다.
사용자가 결제 화면을 닫거나 결제를 진행하지 않는 경우를 처리해야 한다.

#### 선택 이유

- 결제 대기 상태가 무기한 유지되는 문제를 방지할 수 있다.
- 만료 주문을 취소하면서 재고와 쿠폰 예약 상태를 복구할 수 있다.
- 스케줄러 방식은 Spring 환경에서 구현과 이해가 비교적 단순하다.

#### 선택하지 않은 대안

- 만료 처리 없음
- 결제 성공 API 호출 시점에만 만료 여부 확인
- 메시지 큐 또는 지연 큐 기반 만료 처리

#### 대안을 선택하지 않은 이유

만료 처리가 없으면 재고가 장시간 묶여 운영 문제가 발생한다.
결제 성공 API에서만 확인하면 사용자가 다시 접근하지 않는 주문은 계속 남을 수 있다.
메시지 큐나 지연 큐는 더 정교하지만 초기 구현에는 인프라 복잡도가 크다.

#### 기대 효과

- 재고 점유가 오래 방치되는 문제를 줄일 수 있다.
- 운영 안정성을 고려한 주문 상태 관리를 연습할 수 있다.

#### 구현 메모

- 만료 대상은 `PAYMENT_PENDING` 상태이면서 `expires_at`이 현재 시각보다 지난 주문으로 조회한다.
- 만료 주문 조회 시 주문 행을 비관적 락으로 잠가 결제 성공/취소 요청과 같은 주문을 동시에 처리하지 않도록 한다.
- 같은 트랜잭션에서 주문을 `CANCELED`와 `PAYMENT_EXPIRED`로 변경하고, 주문 상품 수량을 상품별로 합산해 재고를 복구한다.
- 테스트 환경에서는 스케줄러 자동 실행을 끄고 서비스 메서드 호출로 만료 처리를 검증한다.

## 007 (2026-06-02)

### 첫 버전 인증/인가는 제외하고 X-Customer-Id 사용

#### 선택

첫 버전에서는 인증/인가를 구현하지 않고, `X-Customer-Id` 헤더로 고객을 식별한다.

#### 배경

초기 구현의 핵심은 장바구니, 주문, 재고, 쿠폰 흐름이다.
인증/인가를 먼저 구현하면 핵심 주문 흐름보다 보안 구성과 토큰 처리에 많은 시간이 들어갈 수 있다.

#### 선택 이유

- 주문과 쿠폰의 고객 소유 관계는 유지하면서 인증 구현 부담을 줄일 수 있다.
- API에서 고객 컨텍스트를 분리해두면 이후 인증/인가 도입 시 전환하기 쉽다.
- 핵심 주문 도메인을 먼저 검증할 수 있다.

#### 선택하지 않은 대안

- Spring Security + JWT 직접 구현
- 외부 인증 서비스 연동

#### 대안을 선택하지 않은 이유

Spring Security와 JWT는 이후 학습 가치가 있지만, 첫 구현 목표와 직접적인 관련성은 낮다.
외부 인증 서비스는 빠르게 붙일 수 있지만, 백엔드 인증/인가 원리를 학습하고 설명하는 데는 직접 구현보다 효과가 낮을 수 있다.

#### 기대 효과

- 핵심 주문 기능을 빠르게 구현할 수 있다.
- 이후 인증/인가 도입 시 `X-Customer-Id`를 인증된 사용자 정보로 교체하는 방향으로 확장할 수 있다.

## 008 (2026-06-03)

### 금액 타입으로 BigDecimal 선택

#### 선택

상품 가격과 할인 금액 등 금액 데이터는 Java `BigDecimal`로 표현한다.

#### 배경

이 프로젝트는 상품 가격, 즉시 할인, 쿠폰 할인, 최종 결제 금액처럼 계산 결과를 주문 스냅샷으로 저장해야 하는 값을 다룬다.
금액 계산은 작은 오차도 사용자 신뢰와 정산 정확성에 영향을 줄 수 있으므로 처음부터 명확한 숫자 표현을 선택할 필요가 있다.

#### 선택 이유

- `BigDecimal`은 십진수 기반 금액 계산을 정확하게 표현할 수 있다.
- 이후 할인, 쿠폰, 결제 금액 계산 로직이 추가되어도 타입을 바꾸지 않아도 된다.
- DB의 `numeric(19, 2)`와 자연스럽게 연결할 수 있다.

#### 선택하지 않은 대안

- `long`
- `double`

#### 대안을 선택하지 않은 이유

`long`은 원화처럼 소수점이 없는 금액만 다룰 때 단순하고 성능상 유리하지만, 할인과 정산 규칙이 늘어날 경우 표현 범위가 좁아질 수 있다.
`double`은 이진 부동소수점 특성상 십진수 금액 계산에서 오차가 생길 수 있어 금액 표현에 적합하지 않다.

#### 기대 효과

- 상품 가격과 할인 금액 계산의 정확성을 유지할 수 있다.
- 주문 금액 스냅샷을 DB와 애플리케이션에서 일관된 타입으로 관리할 수 있다.

## 009 (2026-06-04)

### 장바구니 소유자를 customer_id 값으로 먼저 관리

#### 선택

장바구니 테이블은 별도 Customer 테이블을 참조하지 않고 `customer_id` 값을 직접 저장한다.

#### 배경

첫 버전에서는 인증/인가를 구현하지 않고 `X-Customer-Id` 헤더로 고객을 식별한다.
장바구니와 주문 흐름을 먼저 구현하는 것이 목표이므로 고객 계정 모델을 먼저 확정하지 않는다.

#### 선택 이유

- 인증/인가와 고객 프로필 구현 없이 장바구니 소유 관계를 검증할 수 있다.
- 이후 Customer 도메인을 도입해도 `customer_id` 기준 데이터는 자연스럽게 연결할 수 있다.
- 주문 생성 기능 구현에 필요한 최소 소유자 경계를 먼저 확보할 수 있다.

#### 선택하지 않은 대안

- Customer 엔티티와 테이블을 먼저 생성
- 인증/인가를 먼저 구현한 뒤 장바구니 구현

#### 대안을 선택하지 않은 이유

Customer 테이블과 인증을 먼저 만들면 장바구니와 주문보다 계정 모델 결정이 앞서게 된다.
현재 목표는 주문 처리와 성능 개선 흐름이므로, 고객 식별은 헤더 값으로 단순화한다.

#### 기대 효과

### 재고 예약 시 비관적 락 선택

#### 선택

주문 생성으로 재고를 예약 차감할 때 `stocks` 행을 `PESSIMISTIC_WRITE`로 잠근다.

- 재고 행을 잠근 뒤 검증하고 차감하면 같은 상품에 대한 주문 생성이 순서대로 처리된다.

- 초기 구현에서 동시성 정합성을 설명하기 쉽고, 이후 성능 측정 때 락 대기 병목을 관찰할 수 있다.

- 별도 락 없이 애플리케이션에서만 재고 검증
- 낙관적 락
- 조건부 업데이트

#### 대안을 선택하지 않은 이유

#### 기대 효과

- 이후 성능 개선 단계에서 비관적 락의 처리량, 응답 시간, 락 대기 시간을 측정하고 대안을 비교할 수 있다.

## 012 (2026-06-04)

### 결제 성공 후 장바구니 제거 기준으로 원본 장바구니 상품 ID 사용

#### 선택

주문 상품에 주문 생성 당시 선택된 장바구니 상품 ID를 저장하고, 결제 성공 후 장바구니 정리는 이 ID가 현재 장바구니 항목과 일치할 때만 처리한다.
기존 `PAYMENT_PENDING` 주문 상품은 V5 마이그레이션에서 고객, 상품, 생성 시각을 기준으로 주문 생성 시점에 이미 존재하던 장바구니 상품 ID만 백필한다.
결제 대기 중 같은 장바구니 항목의 수량이 증가한 경우에는 주문 수량만큼만 차감하고 남은 수량은 유지한다.

#### 배경

상품 ID만으로 장바구니 항목을 다시 찾으면, 사용자가 주문 생성에 사용한 장바구니 항목을 삭제한 뒤 같은 상품을 다시 담았을 때 새 장바구니 항목까지 제거될 수 있다.

#### 선택 이유

- 결제 성공 후 제거 대상은 같은 상품이 아니라 주문 생성에 사용된 장바구니 항목이다.
- 원본 장바구니 항목이 이미 삭제된 경우에는 제거할 대상이 없으므로 새 항목을 건드리지 않는 것이 안전하다.
- 장바구니 항목은 이후 삭제될 수 있으므로 외래 키가 아니라 스냅샷 ID로만 보존한다.
- 기존 결제 대기 주문도 배포 직후 동일한 제거 규칙을 따르도록 마이그레이션에서 현재 장바구니 항목을 백필하되, 주문 생성 이후 다시 담긴 항목은 백필하지 않는다.
- 장바구니는 고객별 상품 중복을 허용하지 않으므로, 같은 상품을 추가하면 기존 장바구니 항목 수량이 증가한다. 따라서 결제 성공 후처리는 row 삭제만 하지 않고 주문 수량만큼 차감해야 한다.

#### 기대 효과

- 오래된 결제 대기 주문을 완료해도 사용자가 새로 담은 같은 상품 장바구니 항목이 사라지지 않는다.
- 결제 성공 후처리의 대상 식별 기준을 더 명확하게 설명할 수 있다.

### 고객 보유 쿠폰을 발급 쿠폰 행 락으로 예약

#### 선택

주문 생성 시 요청된 `issued_coupons` 행을 비관적 락으로 조회한 뒤, 유효한 쿠폰을 `RESERVED` 상태로 변경한다.
결제 성공 시 `USED`, 결제 취소 또는 결제 대기 만료 시 `AVAILABLE`로 되돌린다.

#### 배경

- 쿠폰 소유자, 상태, 만료 시간, 타입, 적용 대상을 주문 생성 트랜잭션 안에서 검증할 수 있다.
- 발급 쿠폰 행을 잠그면 같은 쿠폰에 대한 동시 주문 생성이 순서대로 처리된다.
- 주문 생성 실패 시 재고 차감, 주문 저장, 쿠폰 예약이 함께 롤백된다.
- 결제 성공/취소/만료 흐름에서 주문에 연결된 발급 쿠폰을 조회해 상태를 전이할 수 있다.

#### 선택하지 않은 대안

- 별도 락 없이 상태만 확인
- 쿠폰 사용 이력을 별도 테이블에 먼저 기록
- 결제 성공 시점에 쿠폰 사용 처리

#### 대안을 선택하지 않은 이유

별도 락 없이 상태만 확인하면 같은 쿠폰을 동시에 예약할 수 있다.
사용 이력 테이블을 먼저 만들면 아직 발급/조회 기능이 없는 단계에서 구조가 커진다.
결제 성공 시점에만 쿠폰을 사용 처리하면 결제 대기 중 다른 주문이 같은 쿠폰을 사용할 수 있다.

#### 기대 효과

- 쿠폰 중복 사용을 주문 생성 시점에 차단할 수 있다.
- 재고 예약과 쿠폰 예약을 하나의 트랜잭션 정합성 문제로 설명할 수 있다.
- 이후 쿠폰 발급/조회 API를 추가할 때 `Coupon`과 `IssuedCoupon` 구조를 그대로 확장할 수 있다.

### 상품 즉시 할인을 수량별 주문 스냅샷으로 저장

#### 선택

상품 즉시 할인은 상품 1개당 할인 금액으로 정의하고, 주문 생성 시 주문 수량만큼 합산해 `Order`와 `OrderItem`의 할인 금액 스냅샷에 저장한다.

주문 이후 할인 정책이 변경되더라도 이미 생성된 주문의 결제 금액과 할인 내역은 바뀌지 않아야 한다.

#### 선택 이유

- 일반적인 상품 할인은 수량이 늘어나면 할인 금액도 수량만큼 늘어나는 방식이 자연스럽다.
- 주문 당시 적용된 할인 금액을 저장하면 이후 할인 정책 변경과 관계없이 주문 이력을 설명할 수 있다.
- 특정 상품 쿠폰은 즉시 할인 적용 후 남은 상품 1개 금액까지만 적용해 할인 순서를 명확히 유지할 수 있다.

#### 선택하지 않은 대안

- 주문 라인당 즉시 할인을 1회만 적용
- 주문 조회 시점마다 최신 할인 정책으로 금액 재계산

#### 대안을 선택하지 않은 이유

주문 라인당 1회만 적용하면 같은 상품을 여러 개 구매한 고객에게 할인 혜택이 직관적으로 보이지 않을 수 있다.
조회 시점 재계산은 할인 정책 변경 후 과거 주문 금액이 달라지는 문제가 있어 결제 이력과 맞지 않는다.

#### 기대 효과

- 할인 계산 순서와 주문 금액 보존 정책을 명확하게 설명할 수 있다.
- 이후 할인 정책이 복잡해져도 주문 스냅샷 기준의 정산 안정성을 유지할 수 있다.

- 향후 Radix UI 같은 headless 컴포넌트를 일부 도입하더라도 Tailwind와 함께 사용할 수 있다.

- 주문 생성과 결제 성공 시점에 첫 주문 자격을 서비스 로직으로 검증
- 첫 주문 쿠폰 예약 중복을 DB 제약이나 고객 단위 락으로 즉시 해결

#### 대안을 선택하지 않은 이유

첫 주문 여부 컬럼만 추가하면 동시 발급, 다중 결제 대기 주문, 결제 확정 시점 검증까지 해결되지 않는다.
서비스 로직만으로 예약 중복을 막으면 동시 요청에서 빈틈이 생길 수 있고, DB 제약이나 고객 단위 락은 고객 테이블이 없는 현재 구조에서는 어색하다.
따라서 실무에 가까운 설계는 이후 회원가입/고객 도메인 구현 시점에 다시 다루는 것이 낫다.

#### 기대 효과

- 현재 PR에서는 첫 주문 쿠폰 관련 동시성/정책 예외가 사라진다.
- 데모 쿠폰은 일반 쿠폰 정책으로만 설명되어 리뷰 범위가 작아진다.
- 이후 인증/인가 구현 때 첫 주문 쿠폰을 고객 생명주기 정책으로 다시 설계할 수 있다.

## 022 (2026-06-06)

### 데모 자식 데이터는 검증된 데모 상품에만 연결

#### 선택

데모 재고, 상품 즉시 할인, 상품 쿠폰은 `product_id`만으로 부모 상품을 찾지 않고, 데모 상품의 이름, 가격, 상태, 콘텐츠, 카테고리, 설명이 일치하는 row에만 연결한다.
기존 DB에 같은 ID의 다른 상품이 있으면 데모 상품 insert는 건너뛰고, 자식 데이터도 함께 생성하지 않는다.

#### 배경

데모 데이터는 고정 ID `10001`부터 `10005`까지 사용한다.
기존 DB에 같은 ID의 다른 상품이 있으면 상품 insert는 `where not exists` 조건으로 건너뛰지만, 기존 방식은 자식 데이터가 ID만 보고 해당 상품에 붙을 수 있었다.

#### 선택 이유

- 외래키는 부모 row 존재만 보장하고, 그 row가 의도한 데모 상품인지는 보장하지 않는다.
- 시드 데이터는 여러 번 적용되거나 기존 데이터가 있는 DB에 적용될 수 있으므로 idempotent 조건이 부모와 자식 모두에 필요하다.
- 엉뚱한 상품에 데모 할인이나 상품 쿠폰이 붙는 문제는 UI와 주문 금액 계산에 직접 영향을 준다.

#### 기대 효과

- 데모 데이터가 기존 상품 데이터와 충돌해도 잘못된 할인/쿠폰 연결이 발생하지 않는다.
- 마이그레이션 테스트로 ID 충돌 상황을 재현해 회귀를 막을 수 있다.

## 023 (2026-06-06)

### 데모 상품 고정 ID 이후 상품 identity 재시작

#### 선택

데모 상품을 고정 ID로 insert한 뒤, Flyway Java migration에서 `products.id` identity를 현재 `max(id) + 1`로 재시작한다.

#### 배경

PostgreSQL의 identity 컬럼은 명시적으로 지정한 ID insert만으로 자동 발급 sequence가 항상 함께 전진하지 않는다.
따라서 데모 상품 `10001`부터 `10005`를 직접 insert한 뒤 sequence가 낮은 값에 머물면, 이후 관리자 상품 등록 시 이미 존재하는 ID를 다시 발급해 중복 키 오류가 발생할 수 있다.

#### 선택 이유

- 고정 ID를 유지하는 현재 PR 범위에서는 sequence 보정이 가장 작은 수정이다.
- `max(id) + 1`을 사용하면 데모 ID뿐 아니라 기존 DB에 더 큰 상품 ID가 있는 경우도 함께 보호할 수 있다.
- SQL 함수 `setval`은 PostgreSQL 전용이라 H2 기반 마이그레이션 테스트와 호환되지 않아, JDBC 기반 Flyway Java migration으로 공통 처리한다.

#### 기대 효과

- 데모 데이터 적용 이후 새 상품 생성 시 ID 중복 오류를 예방한다.
- 마이그레이션 테스트로 기존 고ID 상품이 있는 DB에서도 자동 발급 ID가 `max(id)` 이후로 이동하는지 검증할 수 있다.

### 첫 상품 이미지는 프론트엔드 로컬 이미지 매핑으로 제공

#### 선택 이유

- 백엔드 API와 DB 스키마를 변경하지 않고도 상품 화면의 시각적 완성도를 높일 수 있다.
- 데모 상품은 고정 ID를 사용하므로 프론트엔드에서 안정적으로 이미지를 매핑할 수 있다.
- 장바구니와 주문 응답처럼 `imageUrl`이 없는 응답에서도 같은 썸네일 컴포넌트를 재사용할 수 있다.
- 사용자가 확정한 상품 이미지를 로컬 자산으로 포함하면 데모 재현성과 화면 신뢰도가 높아진다.
- 실제 이미지 운영 요구가 생기면 `imageUrl` 필드를 추가하는 방향으로 확장할 수 있다.

#### 선택하지 않은 대안

- 상품 응답에 `imageUrl` 필드 추가
- 이미지 바이너리를 DB에 저장
- 외부 임시 이미지 URL 사용

#### 대안을 선택하지 않은 이유

`imageUrl` 추가는 실제 이미지 저장 위치와 운영 방식을 함께 결정해야 하므로 현재 주문 흐름 개선 범위보다 크다.
이미지 바이너리를 DB에 저장하는 방식은 데이터베이스의 책임을 불필요하게 넓히고 정적 자산 캐싱에도 불리하다.
외부 임시 이미지 URL은 데모 재현성과 장기 유지보수성이 낮다.

#### 기대 효과

- API 스키마 변경 없이 프론트엔드 MVP 화면의 상품 식별성이 좋아진다.
- 이후 실제 상품 이미지 인프라를 도입할 때 API 확장 지점을 명확하게 설명할 수 있다.

### 참조 중인 데모 쿠폰은 삭제 대신 만료 처리

#### 선택

데모 데이터 복구 마이그레이션에서 잘못 생성된 상품 쿠폰을 정리할 때, 발급 이력이 없는 쿠폰만 삭제하고 `issued_coupons`에서 참조 중인 쿠폰은 보존하되 만료 처리한다.

#### 배경

기존 `V9`는 데모 상품 ID가 기존 상품과 충돌하면 상품 쿠폰을 의도하지 않은 상품에 연결할 수 있었다.

#### 선택 이유

- 발급 이력이 있는 쿠폰은 더 이상 단순 시드 데이터가 아니라 이력 테이블의 부모 row다.
- `ON DELETE CASCADE`나 발급 이력 삭제는 주문/쿠폰 감사 이력을 잃을 수 있어 복구 마이그레이션의 기본 선택으로 부적절하다.
- 부모 쿠폰을 만료하면 추가 발급과 사용을 막으면서 기존 참조 무결성을 유지할 수 있다.

#### 기대 효과

- 잘못 생성된 데모 쿠폰이 이미 발급된 DB에서도 애플리케이션 시작이 막히지 않는다.
- 발급 이력은 보존되고, 참조 없는 잘못된 데모 쿠폰은 깔끔하게 제거된다.

## 026 (2026-06-07)

### 적용된 Flyway V9 마이그레이션 유지

#### 선택

PR에서는 base 브랜치의 `V9__insert_demo_products_and_coupons.sql`을 수정하지 않고, 추가 정리 작업은 새 `V11` 마이그레이션과 명시적인 로컬 repair 절차로 분리한다.

#### 배경

Flyway는 새 마이그레이션을 실행하기 전에 이미 적용된 versioned migration의 체크섬을 먼저 검증한다.
따라서 base 브랜치의 현재 `V9`를 이미 적용한 환경에서 PR이 `V9` 내용을 바꾸면, `V11` 정리 로직에 도달하기 전에 checksum mismatch로 시작이 실패한다.

#### 선택 이유

- versioned migration은 적용 후 변경하지 않는 것이 Flyway 운영 원칙이다.
- 오래된 로컬 개발 DB의 과거 `V9` 체크섬 문제는 PR 코드가 아니라 DB reset 또는 명시적인 Flyway repair로 해결해야 한다.
- `V11`은 base `V9`를 정상 적용한 DB에서도 안전하게 no-op 또는 데이터 정리만 수행해야 한다.
- 데모 쿠폰명 변경은 이름, 타입, 금액만으로 실제 쿠폰과 구분하기 어려우므로 seed 고정 timestamp와 만료 시각까지 함께 확인한다.

#### 기대 효과

- 이미 base `V9`를 적용한 환경에서 PR 머지 후 checksum mismatch가 발생하지 않는다.
- 과거 로컬 DB 복구 절차와 코드 마이그레이션 책임을 분리해 설명할 수 있다.
- 같은 이름과 금액을 가진 실제 쿠폰이 있어도 데모 데이터 정리 대상에 잘못 포함되지 않는다.

### 최종 데모 할인과 관찰 패널 범위 정리

최종 데모 즉시 할인은 `V14__apply_final_demo_discounts_and_coupon_cleanup.sql`에서 Savoia S-21 수상비행기 피규어 5000원, 묘코 마스코트 봉제 인형 3000원으로 적용한다.
Savoia 즉시 할인은 기존 할인 row가 없을 때만 새로 추가하고, 묘코 즉시 할인은 기존 seed 할인 값과 일치하는 row만 최종 할인으로 갱신한다.
드롭 기념 전체 상품 쿠폰은 5000원 쿠폰만 발급 가능 상태로 유지하고, 3000원 쿠폰은 seed 전용 `expires_at`, `created_at`, `updated_at`까지 일치할 때만 정리한다.
정리 대상 seed 쿠폰에 발급 이력이 없으면 삭제한다.
발급 이력이 있으면 `AVAILABLE` 발급 쿠폰만 만료 처리하고, 쿠폰 원본은 이후 발급 정책 상태로 신규 발급을 중단한다.
결제 대기 주문에 연결된 `RESERVED` 발급 쿠폰은 주문 완료/취소/만료 흐름을 마칠 수 있도록 그대로 둔다.
상태 관찰 패널은 고객 ID, 최근 API, 상품 재고, 장바구니, 보유 쿠폰만 보여주는 시연용 보조 패널로 제한한다.

#### 배경

상품별 즉시 할인은 사용자가 지정한 상품과 금액만 대표 가격에 반영되어야 한다.
또한 같은 성격의 전체 상품 쿠폰이 3000원과 5000원으로 동시에 노출되면 데모 사용자가 어떤 쿠폰을 써야 하는지 헷갈릴 수 있다.
기존 상태 관찰 패널은 주문/결제 요약까지 섞여 있어 프론트 시연 중 핵심 변화인 API 호출, 재고, 장바구니, 쿠폰 상태를 빠르게 보기 어렵다.

#### 선택 이유

- 적용된 Flyway 마이그레이션은 유지하고 새 버전으로 최종 상태를 만든다.
- `issued_coupons`가 참조하는 쿠폰 원본은 물리 삭제할 수 없으므로, 참조가 있으면 미예약 발급 쿠폰만 만료 처리하고 원본은 별도 발급 정책 상태로 제어한다.
- `RESERVED` 발급 쿠폰은 주문 생명주기 메서드가 요구하는 상태이므로 마이그레이션에서 직접 만료시키지 않는다.
- 상품 ID만으로 기존 할인 row를 데모 seed라고 볼 수 없으므로, 즉시 할인 갱신도 seed 값과 메타데이터가 확인되는 row로 제한한다.
- 이름, 타입, 금액은 사용자 생성 쿠폰과 겹칠 수 있으므로 seed timestamp를 함께 조건에 넣어 실제 운영성 row를 건드리지 않는다.
- 주문 상태는 주문 목록/상세 화면의 책임으로 두고, 오른쪽 패널은 현재 고객의 쇼핑 흐름 관찰에 집중한다.

#### 기대 효과

- 상품 목록과 상세에서 의도한 두 상품만 즉시 할인으로 표시된다.
- 발급 가능 쿠폰 목록에서 중복 성격의 3000원 전체 쿠폰이 사라진다.
- 상태 관찰 패널이 데모 중 확인해야 할 정보만 보여 더 읽기 쉬워진다.

## 030 (2026-06-07)

### 쿠폰 원본 발급 정책 상태 분리

#### 선택

`coupons`에 `status` 컬럼을 추가해 쿠폰 원본의 신규 발급 정책을 `ACTIVE`, `STOPPED`로 관리한다.
발급 가능 쿠폰 조회와 쿠폰 발급 API는 `ACTIVE` 상태이고 만료 시간이 지나지 않은 쿠폰 원본만 대상으로 삼는다.
최종 데모에서 제외된 3000원 전체 상품 seed 쿠폰은 발급 이력이 있으면 삭제하지 않고 `STOPPED`로 전환한다.

#### 배경

기존 설계는 `expires_at` 하나로 쿠폰 사용 만료와 신규 발급 중단을 함께 표현했다.
이 때문에 발급 이력이 있어 삭제할 수 없는 쿠폰을 보존하면서 신규 발급만 막아야 하는 상황에서, 만료 시간을 과거로 보내는 우회가 필요했다.
하지만 만료 시간은 사용 가능 기간을 뜻하고, 발급 중단은 운영 정책이므로 두 의미를 분리하는 편이 유지 보수와 설명에 더 적합하다.

#### 선택 이유

- 쿠폰 원본의 발급 정책 상태와 고객 보유 쿠폰의 사용 상태를 분리해 도메인 의미를 명확히 한다.
- 발급 이력이 있는 쿠폰 원본은 참조 무결성과 감사 이력을 위해 보존하면서도 신규 발급은 서버 규칙으로 차단할 수 있다.
- `expires_at`을 과거 값으로 조정하는 임시 처리보다 운영자가 이해하기 쉬운 상태 전이를 제공한다.

#### 기대 효과

- 최종 데모에서는 5000원 전체 상품 쿠폰만 신규 발급 대상으로 노출된다.
- 3000원 seed 쿠폰 이력이 있는 DB에서도 주문 생명주기를 깨지 않고 신규 발급을 막을 수 있다.
- 이후 관리자 쿠폰 비활성화 API를 추가할 때 같은 `STOPPED` 상태를 재사용할 수 있다.

## 031 (2026-06-07)

### 인기 상품 재고 차감에 조건부 업데이트 적용

#### 선택

주문 생성의 재고 예약 차감은 `stocks` 행을 비관적 락으로 먼저 조회한 뒤 엔티티 수량을 차감하는 방식에서, `quantity >= 주문 수량` 조건을 가진 DB 업데이트 쿼리로 변경한다.

#### 배경

한정판 상품 오픈 직후 같은 상품에 주문 생성 요청이 몰리는 상황을 측정했다.
기준 측정에서 주문 500건, 동시성 100 조건은 모두 성공했고 초과 판매도 없었지만, p95 응답 시간이 1,097.51ms로 1차 목표인 1초를 넘었다.
현재 구현은 재고 행을 읽고 잠근 뒤 주문 상품 생성과 주문 저장으로 이어져, hot row에 요청이 몰릴수록 뒤 요청의 락 대기 시간이 커질 수 있었다.

#### 선택 이유

- 조건부 업데이트는 재고 검증과 차감을 하나의 DB 문장으로 처리해 read-check-write 구간을 줄인다.
- PostgreSQL의 `UPDATE`도 row-level lock을 사용하므로 정합성 보장은 유지된다.
- 업데이트 결과가 0건이면 재고 부족으로 판단할 수 있어 초과 판매를 막을 수 있다.
- 여러 상품 주문에서는 상품별 수량을 합산해 차감하고, 일부 실패 시 같은 트랜잭션에서 예외를 던져 전체 롤백할 수 있다.

#### 선택하지 않은 대안

- 비관적 락 유지
- 낙관적 락과 재시도
- Redis 같은 외부 재고 예약 저장소

#### 대안을 선택하지 않은 이유

비관적 락 유지는 정합성이 직관적이지만 이번 측정에서 p95 응답 시간이 목표를 넘었다.
낙관적 락은 충돌이 적은 경우에 유리하지만 인기 상품 hot row처럼 충돌이 높은 상황에서는 재시도 비용이 커질 수 있다.
Redis는 더 큰 구조 변경과 장애 시 정합성 설계가 필요하므로, 현재 단계에서는 PostgreSQL 트랜잭션 안에서 설명 가능한 개선을 먼저 선택했다.

#### 기대 효과

- 초과 판매 0건을 유지하면서 재고 차감 임계 구역을 줄인다.
- 로컬 동시성 100 측정에서 주문 생성 p95 응답 시간을 1,097.51ms에서 962.91ms로 낮췄다.
- 처리량은 5,647.27건/분에서 7,114.73건/분으로 개선됐다.

#### 한계와 후속 검토

로컬 측정에서 기동 직후 첫 재측정 값이 튄 만큼, 다음 성능 개선에서는 측정 전 데이터 초기화, 반복 측정 평균, DB 락 대기와 커넥션 풀 지표를 함께 확인한다.
조건부 업데이트 이후에도 주문 저장과 쿠폰 예약은 같은 트랜잭션에 남아 있으므로, 다음 단계에서는 트랜잭션 범위와 쿼리 수를 분리해 본다.
