# 요구사항 정의

이 문서는 이커머스 주문 흐름의 첫 구현 기준을 정리한다.
구현 중 정책이 변경되면 이 문서를 함께 갱신한다.

## 서비스 컨셉

- 콘텐츠 IP 기반 한정판 굿즈를 판매하는 드롭 커머스 플랫폼으로 시작한다.
- 판매 대상은 웹툰, 웹소설, 영화, 드라마, 음악 등 콘텐츠 IP와 연결된 실물 굿즈다.
- 초기 상품 예시는 한정판 아트북, 포스터, 키링, 스티커팩, OST 앨범, 한정판 패키지 세트다.
- 초기에는 단일 운영자가 상품과 이벤트를 관리한다고 가정한다.
- 파트너사, 창작자, 이벤트 회사가 직접 입점하는 구조는 이후 확장 후보로 둔다.
- 첫 구현에서는 콘텐츠 IP, 이벤트, 파트너사를 별도 도메인으로 분리하지 않고 상품의 설명과 분류 정보로 다룬다.

## 1. 현재 목표

- 장바구니 기반 주문 생성 기능을 구현한다.
- 주문 생성 후 결제 대기 상태를 만들고, 가짜 결제 성공/취소 흐름을 구현한다.
- 주문 과정에서 상품 상태, 재고, 쿠폰 사용 가능 여부를 검증한다.
- 주문 기능 구현 후 분당 100건의 주문 처리 가능 여부를 측정한다.

## 2. 구현 범위

### 1차 기능 목록

- 상품 및 재고
- 장바구니
- 주문 생성
- 재고 예약
- 가짜 결제 성공/취소
- 결제 대기 주문 만료 처리
- 고객 보유 쿠폰 사용
- 상품 즉시 할인 적용
- 쿠폰 발급/조회

### 이후 구현 예정

- 인증/인가
- 실제 결제 API 연동
- 콘텐츠 IP 및 이벤트 관리
- 파트너사 또는 창작자 입점 관리
- 배송 기능
- 주문 완료 후 취소/반품
- 바로 구매
- 가격 변경 이력 관리

## 3. 고객과 인증

- 첫 버전에서는 인증/인가를 구현하지 않는다.
- API 요청에서 `customerId`를 받아 고객을 식별한다.
- 장바구니, 주문, 쿠폰은 `customerId` 기준으로 소유자를 구분한다.
- 이후 인증/인가 도입 시 요청 값의 `customerId` 대신 인증된 사용자 정보를 사용한다.

## 4. 상품과 재고

### 상품 상태

- 상품 상태는 `ON_SALE`, `STOPPED`로 시작한다.
- `ON_SALE` 상태의 상품만 주문할 수 있다.
- 품절은 별도 상품 상태로 관리하지 않고 재고 수량으로 판단한다.

### 재고 정책

- 주문 생성 시점에 상품 재고를 검증한다.
- 현재 재고가 주문 수량 이상이면 주문할 수 있다.
- 주문 완료 후 재고가 0이 되는 것은 허용한다.
- 현재 재고가 주문 수량보다 적으면 주문할 수 없다.
- 주문 생성이 성공하면 결제 대기 상태에서도 재고를 즉시 차감한다.
- 결제 취소 또는 결제 대기 만료 시 차감했던 재고를 복구한다.

## 5. 장바구니

- 고객은 상품을 장바구니에 담을 수 있다.
- 고객당 같은 상품은 장바구니에 한 줄만 존재한다.
- 같은 상품을 다시 담으면 기존 장바구니 수량이 증가한다.
- 장바구니 수량은 현재 재고보다 크게 변경할 수 없다.
- 장바구니 상품 추가 또는 수량 변경 후 최종 수량이 현재 재고보다 크면 실패한다.
- 장바구니 상품 수정과 삭제는 요청 고객의 장바구니에 속한 상품에만 허용한다.
- 장바구니 조회 시 상품의 현재 판매 상태와 재고 상태를 함께 보여준다.
- 판매 중지 상품이나 재고 부족 상품은 장바구니에 표시하되 주문 선택은 불가능하다.
- 사용자는 장바구니에서 주문할 상품을 선택할 수 있다.
- 전체 선택을 통해 장바구니의 주문 가능 상품 전체를 주문할 수 있다.
- 백엔드는 주문 생성 시점에 상품 상태와 재고를 다시 검증한다.

## 6. 주문

### 주문 생성

- 주문은 장바구니에서 선택한 상품을 기준으로 생성한다.
- 주문 상품마다 수량을 가진다.
- 주문 생성 시 상품 상태, 재고, 쿠폰 사용 가능 여부를 검증한다.
- 주문은 전체 성공 또는 전체 실패로 처리한다.
- 일부 상품 또는 쿠폰 검증이 실패하면 주문 전체를 실패시킨다.
- 주문 생성 실패 시 재고 차감, 쿠폰 예약, 주문 저장 등 어떤 변경도 남기지 않는다.
- 주문 생성 성공 시 주문 상태는 `PAYMENT_PENDING`이 된다.
- 주문 생성 성공 시 선택 상품의 재고를 즉시 차감한다.
- 주문 생성 성공 시 고객 보유 쿠폰은 `RESERVED` 상태로 예약한다.

### 주문 상태

- `PAYMENT_PENDING`: 결제 대기
- `COMPLETED`: 주문 완료
- `CANCELED`: 주문 취소

### 주문 취소 사유

- `PAYMENT_CANCELED`: 사용자가 결제를 취소함
- `PAYMENT_EXPIRED`: 결제 대기 시간이 만료됨

### 주문 금액 저장

주문에는 주문 당시 금액 정보를 저장한다.

- 상품 원금액 합계
- 상품 즉시 할인 금액 합계
- 고객 보유 쿠폰 할인 금액 합계
- 최종 결제 금액

주문 상품 라인에는 주문 당시 상품 정보를 저장한다.

- 상품 주문 당시 가격
- 주문 수량
- 상품 원금액
- 상품 즉시 할인 금액
- 특정 상품 쿠폰 할인 금액
- 라인 최종 금액

## 7. 가짜 결제

- 실제 결제 API는 이후 연동한다.
- 첫 버전에서는 가짜 결제 성공/취소 API로 결제 흐름을 구현한다.
- 결제 금액이 0원이어도 가짜 결제 성공 API를 호출해 동일한 상태 흐름을 따른다.

### 결제 성공

- 결제 성공 API는 `PAYMENT_PENDING` 주문에만 호출할 수 있다.
- 결제 성공 시 결제 대기 만료 여부를 검증한다.
- 결제 대기 시간이 지나지 않았다면 주문 상태를 `COMPLETED`로 변경한다.
- 결제 성공 시 예약된 고객 보유 쿠폰을 `USED` 상태로 변경한다.
- 결제 성공 시 주문한 장바구니 상품을 장바구니에서 제거한다.

### 결제 취소

- 결제 취소 API는 `PAYMENT_PENDING` 주문에만 호출할 수 있다.
- 결제 취소 시 주문 상태를 `CANCELED`로 변경한다.
- 결제 취소 사유는 `PAYMENT_CANCELED`로 기록한다.
- 결제 취소 시 차감했던 재고를 복구한다.
- 결제 취소 시 예약된 고객 보유 쿠폰을 `AVAILABLE` 상태로 되돌린다.
- `COMPLETED` 주문의 취소/반품은 첫 구현 범위에서 제외한다.

## 8. 결제 대기 만료

- 결제 대기 주문의 유효 시간은 10분이다.
- 스케줄러는 1분마다 만료된 `PAYMENT_PENDING` 주문을 찾는다.
- 결제 대기 시간이 10분을 초과한 주문은 `CANCELED` 상태로 변경한다.
- 만료 취소 사유는 `PAYMENT_EXPIRED`로 기록한다.
- 만료 처리 시 차감했던 재고를 복구한다.
- 만료 처리 시 예약된 고객 보유 쿠폰을 `AVAILABLE` 상태로 되돌린다.
- 결제 성공 API에서도 만료 여부를 한 번 더 검증한다.
- 만료된 주문에 결제 성공 API가 호출되면 주문을 취소 처리하고 실패 응답을 반환한다.

## 9. 쿠폰과 할인

### 쿠폰 종류

고객 보유 쿠폰은 고객이 발급받고 주문 시 직접 사용하는 쿠폰이다.

- 전체 상품 쿠폰: 주문 전체 금액에 1회 적용한다.
- 특정 상품 쿠폰: 특정 상품 1개에 적용한다.

상품 즉시 할인은 상품에 설정된 자동 할인이다.

- 고객이 직접 발급받지 않는다.
- 고객 쿠폰 발급/사용 이력을 남기지 않는다.
- 주문 할인 내역에는 즉시 할인 금액을 저장한다.
- 상품당 최대 1개의 즉시 할인 정책만 적용한다.

### 고객 보유 쿠폰 사용 규칙

- 쿠폰이 없어도 주문할 수 있다.
- 한 주문에는 전체 상품 쿠폰을 최대 1개 사용할 수 있다.
- 한 주문에는 상품별로 특정 상품 쿠폰을 최대 1개씩 사용할 수 있다.
- 전체 상품 쿠폰과 특정 상품 쿠폰은 함께 사용할 수 있다.
- 고객 보유 쿠폰과 상품 즉시 할인은 함께 적용할 수 있다.
- 특정 상품 쿠폰은 주문에 해당 상품이 여러 개 있어도 상품 1개에만 할인된다.
- 전체 상품 쿠폰은 주문 전체 금액에 1회 적용된다.

### 쿠폰 상태

- `AVAILABLE`: 사용 가능
- `RESERVED`: 결제 대기 주문에 예약됨
- `USED`: 사용 완료
- `EXPIRED`: 만료됨

### 쿠폰 검증 조건

주문 생성 시 고객 보유 쿠폰은 아래 조건을 모두 만족해야 한다.

- 주문 고객이 보유한 쿠폰이다.
- 쿠폰 상태가 `AVAILABLE`이다.
- 쿠폰 만료 시간이 지나지 않았다.
- 쿠폰 타입과 적용 대상이 주문 상품과 일치한다.
- 할인 금액이 0보다 크다.

주문 생성 시점에 유효해 `RESERVED` 처리된 쿠폰은 결제 대기 시간 안에서는 만료 시간이 지나도 해당 주문에 사용할 수 있다.
결제 대기 시간이 만료되면 주문이 취소되고 쿠폰 예약도 해제된다.

### 만료 쿠폰

- 만료된 쿠폰은 사용할 수 없다.
- 만료된 쿠폰은 삭제하지 않는다.
- 쿠폰 조회 시 만료 상태를 표시하거나 사용 가능 목록에서 제외한다.
- 만료 상태 자동 변경 방식은 쿠폰 기능 구현 시 확정한다.

### 쿠폰 발급

- 이벤트 페이지의 쿠폰 발급 버튼을 통해 고객 보유 쿠폰을 발급할 수 있다.
- 쿠폰 중복 발급 허용 여부는 쿠폰 발급 기능 구현 전에 확정한다.

## 10. 금액 계산 순서

할인 방식은 정액 할인부터 시작한다.
할인 적용 후 금액은 0원 미만이 될 수 없다.

상품별 금액 계산 순서는 다음과 같다.

```text
상품 원금액
- 상품 즉시 할인
- 특정 상품 쿠폰 할인
= 상품별 할인 후 금액
```

주문 전체 금액 계산 순서는 다음과 같다.

```text
상품별 할인 후 금액 합계
- 전체 상품 쿠폰 할인
= 최종 결제 금액
```

## 11. 실패 처리

### 주문 생성 실패

아래 상황에서는 주문 전체를 실패시킨다.

- 판매 중이 아닌 상품이 포함됨
- 재고가 부족한 상품이 포함됨
- 고객이 보유하지 않은 쿠폰 사용 요청
- 이미 사용된 쿠폰 사용 요청
- 만료된 쿠폰 사용 요청
- 예약 중인 쿠폰 사용 요청
- 쿠폰 타입 또는 적용 대상이 주문과 일치하지 않음

주문 생성 실패 응답에는 가능한 경우 아래 정보를 포함한다.

- 실패 상품 ID
- 실패 쿠폰 ID
- 실패 사유 코드
- 사용자 메시지
- 현재 재고

### 실패 사유 코드

초기 실패 사유 코드는 다음을 기준으로 시작한다.

- `PRODUCT_NOT_ON_SALE`
- `OUT_OF_STOCK`
- `CART_ITEM_NOT_FOUND`
- `CART_ITEM_NOT_SELECTABLE`
- `COUPON_NOT_OWNED`
- `COUPON_NOT_AVAILABLE`
- `COUPON_ALREADY_USED`
- `COUPON_RESERVED`
- `COUPON_EXPIRED`
- `COUPON_TARGET_MISMATCH`
- `ORDER_NOT_PAYMENT_PENDING`
- `ORDER_PAYMENT_EXPIRED`

## 12. 구현 순서

구현은 기능 단위로 나누어 진행한다.

```text
1. 상품/재고 기본 모델
2. 장바구니
3. 주문 생성 및 재고 예약
4. 가짜 결제 성공/취소
5. 결제 대기 주문 만료 처리
6. 고객 보유 쿠폰 예약/사용
7. 상품 즉시 할인 적용
8. 쿠폰 발급/조회
9. 성능 측정 및 개선
```

구현 순서는 실제 개발 중 의존성과 학습 필요성에 따라 조정할 수 있다.
