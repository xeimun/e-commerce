# Feature Flow

> 참고: Codex가 개인 skill을 자동 인식하지 못하는 환경에서도 동일한 절차를 따르도록 임시로 프로젝트 문서에 함께 둔다.

기능 하나를 문서 확인부터 구현, 검증, 문서 갱신, 커밋, push, PR 생성까지 일관되게 완료한다.

## 기본 원칙

- 이 스킬이 로드되면 기능 하나를 끝까지 완료하는 실행 흐름을 따른다.
- 프로젝트 문서, 코드 상태, 브랜치 상태, PR 상태, 사용자 지시가 서로 맞지 않거나 애매하면 임의로 진행하지 말고 멈춰서 질문한다.
- 상위 지시, 실행 환경 규칙, 저장소 문서, 사용자 요청이 충돌하면 더 높은 우선순위의 지시를 따른다.
- 열린 미병합 PR이 있으면 다음 기능 구현을 바로 시작하지 않는다. 먼저 사용자에게 기존 PR merge를 기다릴지, 해당 PR 위에서 이어갈지, 다른 작업을 할지 확인한다.
- 기능 완료 후에는 다음 기능 구현 때 참고할 수 있도록 관련 문서와 진행 현황을 갱신한다.

## 워크플로우

1. 실제 저장소 루트를 확인한다.
   - 현재 cwd가 실제 저장소가 아닐 수 있으므로 `git status`, `rg --files`, 문서 위치로 실제 repo root를 확인한다.
   - cwd가 다르면 이후 명령은 실제 repo path를 명시해 실행한다.

2. 프로젝트 규칙과 요구사항 문서를 읽는다.
   - `AGENTS.md`가 있으면 작업 규칙, Git/PR 원칙, 테스트 명령을 확인한다.
   - `docs/requirements.md`가 있으면 구현 순서와 진행 현황을 우선 확인한다.
   - 필요한 경우 `docs/api-spec.md`, `docs/domain-model.md`, `docs/decision-log.md`, `docs/learning-notes.md`를 함께 확인한다.

3. 현재 작업 상태를 확인한다.
   - 현재 브랜치와 uncommitted changes를 확인한다.
   - `main` 또는 기본 브랜치가 원격과 동기화되어 있는지 확인한다.
   - GitHub 도구가 가능하면 열린 미병합 PR을 확인한다.
   - 열린 PR 또는 충돌 가능성이 있는 작업이 있으면 멈추고 사용자에게 확인한다.

4. 다음 기능을 결정한다.
   - `docs/requirements.md`의 진행 현황 체크리스트가 있으면 첫 번째 미완료 항목을 다음 기능으로 본다.
   - 진행 현황이 없고 구현 순서만 있으면 구현 순서를 기준으로 코드 상태와 비교해 다음 기능을 판단한다.
   - 다음 기능이 명확하지 않거나 비즈니스 규칙이 애매하면 구현 전에 질문한다.

5. 기능 브랜치를 준비한다.
   - 저장소 문서의 브랜치 네이밍 규칙을 따른다.
   - 규칙이 없으면 상위 지시나 실행 환경의 기본 브랜치 prefix를 따르고, 그마저 없으면 `feat/<short-feature-name>` 형식을 사용한다.
   - 사용자가 명시하지 않았다면 `main`에서 직접 기능 구현을 시작하지 않는다.

6. 기능을 구현한다.
   - 기존 코드 구조, 프레임워크, 테스트 스타일을 따른다.
   - 요청 범위와 다음 기능 범위에 필요한 변경만 수행한다.
   - API, 도메인, DB 스키마, 에러 응답, 테스트를 기능 단위로 맞춰 구현한다.

7. 검증한다.
   - 프로젝트 문서에 적힌 테스트 명령을 실행한다.
   - 기능 변경이 컴파일/패키징에 영향을 주면 빌드도 실행한다.
   - DB 마이그레이션이 있으면 테스트/빌드 또는 문서화된 로컬 DB 흐름으로 검증한다.
   - 실패 원인이 불명확하면 임의로 넘어가지 말고 원인과 다음 행동을 보고한다.

8. 관련 문서를 갱신한다.
   - 요구사항 변경은 `docs/requirements.md`에 반영한다.
   - 도메인 변경은 `docs/domain-model.md`에 반영한다.
   - API 변경은 `docs/api-spec.md`에 반영한다.
   - 중요한 기술 선택은 `docs/decision-log.md`에 반영한다.
   - 구현에 연결되는 학습 내용은 `docs/learning-notes.md`에 반영한다.
   - 성능 측정과 개선은 `docs/performance-report.md`에 반영한다.

9. 진행 현황을 갱신한다.
   - `docs/requirements.md`에 진행 현황 체크리스트가 있으면 완료한 기능을 체크한다.
   - 구현 순서는 있지만 진행 현황이 없으면, 적절할 때 짧은 체크리스트를 추가한다.
   - 진행 현황은 구현 순서와 같은 기능 단위로 유지한다.

10. 커밋, push, PR을 진행한다.
   - 검증이 통과했을 때만 완료 커밋을 만든다.
   - 저장소의 커밋 메시지 규칙을 따른다. 규칙이 없으면 Conventional Commits를 사용한다.
   - 기능 브랜치를 원격에 push한다.
   - 저장소의 PR 템플릿으로 PR을 생성한다.

## 완료 보고

기능 구현이 끝나면 최종 응답에 다음 내용을 포함한다.

- 이번에 구현한 기능 요약
- 현재까지 완료된 기능 목록
- 다음에 우선적으로 구현할 기능 1개
- 테스트와 빌드 검증 결과
- 생성한 PR 링크가 있으면 PR 링크

현재까지 완료된 기능 목록은 `docs/requirements.md`의 진행 현황 체크리스트를 기준으로 정리한다.
다음 기능은 같은 체크리스트에서 첫 번째 미완료 항목을 우선 제안한다.
진행 현황 체크리스트가 없으면 구현 순서와 코드 상태를 기준으로 추론하되, 확실하지 않으면 사용자에게 확인한다.

완료 보고 예시:

```md
이번에 장바구니 기능을 구현했습니다.

현재까지 완료된 기능:
- 상품/재고 기본 모델
- 장바구니

다음 우선 구현 기능:
- 주문 생성 및 재고 예약

검증:
- 테스트 통과
- 빌드 통과

PR:
- #3 feat: 장바구니 기능 추가
```
## 반드시 멈추고 질문할 상황

- 열린 미병합 PR이 있다.
- 다음 기능이 문서에서 명확하지 않다.
- 문서상 다음 기능과 코드 상태가 다르다.
- 사용자 지시와 프로젝트 문서가 충돌한다.
- 요구사항이 비즈니스 규칙에 영향을 주는데 애매하다.
- 테스트 또는 빌드 실패 원인이 불명확하다.
- push 또는 PR 생성이 인증, 권한, 원격 상태 문제로 실패한다.
