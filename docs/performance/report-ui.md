# 성능 리포트 UI 설계

이 문서는 프론트엔드 `/report` 화면에서 성능 측정 결과를 어떻게 보여줄지 정리한다.
실제 측정 수치와 개선 과정의 원천 자료는 `docs/performance/report.md`에 기록하고, 이 문서는 화면 정보 구조와 시각화 기준에 집중한다.

## 목적

- 멘토링에 참여하는 멘토와 멘티, 채용담당자가 성능 개선 성과를 빠르게 이해할 수 있게 한다.
- 성능 개선 결과를 단순 수치 나열이 아니라 문제 상황, 적용한 CS 개념, 개선 전후 지표, 정합성 검증 흐름으로 보여준다.
- 채용담당자는 상단 성과를 빠르게 읽고, 현직자는 하단 상세 근거를 따라갈 수 있게 한다.

## 대상 독자

- 멘토링에 참여하는 멘토
- 멘토링에 참여하는 멘티
- 채용담당자 또는 포트폴리오 검토자

## 데이터 출처

- 성능 개선 후보와 진행 상태: `docs/performance/plan.md`
- 실제 측정 결과와 해석: `docs/performance/report.md`
- 화면에는 완료된 성능 개선 결과만 노출한다.
- 다음 성능 개선 후보나 아직 수행하지 않은 항목은 `/report` 화면에 표시하지 않는다.

## 화면 구조

`/report` 화면은 공통 측정 조건, 완료된 성능 개선 탭, 선택된 성능 개선 상세 리포트로 구성한다.
리포트 페이지에서는 오른쪽 상태 관찰 패널을 숨겨 본문 가독성을 우선한다.

```text
/report

Performance Report
성능 리포트
공통 측정 조건
성능 개선별 탭
선택된 성능 개선 상세 리포트
```

### 상단 설명

상단 설명은 리포트의 목적을 짧게 안내한다.

```text
완료된 성능 개선의 문제 상황, 적용한 CS 개념, 개선 전후 지표와 정합성 검증을 비교합니다.
```

### 공통 측정 조건

공통 영역은 모든 성능 개선에 반복되는 측정 조건만 짧게 표시한다.

- 측정 환경: 로컬 Windows, Spring Boot, PostgreSQL Docker Compose
- 측정 도구: k6
- 비교 방식: 같은 데이터와 부하 조건에서 개선 전후 비교

상품 ID, 재고 수, VU 수처럼 특정 실험에 속한 조건은 상세 측정값 토글 안에서 다룬다.

### 성능 개선별 탭

상세 리포트는 성능 개선 단위로 탭을 나누어 보여준다.
서로 다른 성능 개선은 사용자 상황, 측정 조건, 병목 지점이 달라질 수 있으므로 하나의 차트에 무리하게 합치지 않는다.

- 탭에는 완료된 성능 개선만 표시한다.
- 탭 이름은 `성능개선 1`, `성능개선 2`처럼 짧게 표시한다.
- 탭 내부 제목은 성과 중심 문장으로 표시한다.
- 이후 성능 개선이 완료될 때마다 탭을 1개씩 추가한다.
- 완료되지 않은 개선 후보명은 탭 예시나 비활성 탭으로도 노출하지 않는다.

현재 첫 성능 개선의 탭 내부 제목은 아래 기준으로 표시한다.

```text
초과 판매 0건 유지하며 주문 생성 처리량 34.8% 개선
```

## 상세 리포트 구성

선택된 탭의 상세 영역은 아래 순서로 배치한다.

1. 채용담당자가 바로 이해할 수 있는 성과 헤드라인
2. 문제 상황과 개선 접근 요약
3. 해당 성능 개선의 측정 조건
4. 핵심 지표 차트
5. 상세 측정값 토글
6. 병목 가설
7. 개선 방법과 이유
8. 정합성 검증
9. 측정 한계

측정 한계는 선택 항목이다.
공통 한계가 아니라 해당 개선에서 실제로 남은 분석 한계가 있을 때만 표시한다.

## 탭 내부 측정 조건

공통 측정 조건은 모든 실험에 반복되는 환경만 보여준다.
각 탭에는 해당 성능 개선의 부하 조건을 별도로 표시해, 화면만 읽어도 측정값을 해석하고 재현할 수 있게 한다.

첫 번째 성능 개선은 아래 조건을 표시한다.

- 대상 상품: 상품 10001
- 부하 방식: k6 shared-iterations, VU 100
- 주문 단위: 고객별 장바구니 1개, 주문 수량 1개, 쿠폰 없음
- 충분한 재고 조건: 초기 재고 1000개, 주문 생성 500건
- 재고 소진 조건: 초기 재고 100개, 주문 생성 200건

## 차트 구성

차트는 전후 비교가 쉬운 구성을 우선한다.
개선 차이가 너무 작게 보이지 않도록 0부터 시작하는 축 대신 관찰 구간 기준 축을 사용할 수 있다.
이 경우 차트 근처에 축 범위를 반드시 표시한다.
대표 지표는 성능 개선마다 달라질 수 있으므로 지표 성격에 맞는 차트를 선택한다.

### 대표 지표

첫 번째 성능 개선의 대표 지표는 주문 생성 처리량이다.

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| 주문 생성 처리량 | 76.97건/초 | 103.76건/초 | 34.8% 증가 |

현재 화면에서는 처리량의 개선 전후 차이를 세로 막대 차트로 표시한다.
처리량 차트는 70-110건/초 범위를 기준으로 표시한다.

### 응답 시간

응답 시간은 평균, p95, p99를 함께 보여준다.
응답 시간은 낮을수록 좋은 지표이므로 처리량과 색상, 라벨을 구분한다.

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| 평균 응답 시간 | 1,179.77ms | 870.26ms | 26.2% 감소 |
| p95 응답 시간 | 1,610.89ms | 1,342.18ms | 16.7% 감소 |
| p99 응답 시간 | 1,630.56ms | 1,450.14ms | 11.1% 감소 |

응답 시간 차트는 800-1700ms 범위를 기준으로 표시한다.
필요한 경우 차트 아래에 짧은 결과 해석 문장을 표시한다.

```text
처리량과 p95는 개선됐지만 p99 개선폭은 작아 꼬리 지연 요인은 남아 있을 수 있음.
```

### 상세 측정값

상세 측정값은 기본 접힘 상태의 토글로 제공한다.
성과만 확인하려는 사용자는 지나칠 수 있고, 수치를 확인하려는 사용자는 펼쳐볼 수 있게 한다.

토글 안에는 아래 두 표를 모두 포함한다.

- 충분한 재고 조건
- 재고 소진 조건

## 하단 상세 설명

차트와 상세 측정값 아래에는 현직자가 궁금해할 판단 과정을 짧게 배치한다.

### 1. 병목 가설

기준 측정 결과에서 어떤 이유로 병목 가설을 세웠는지 설명한다.
운영 장애를 직접 관찰한 것이 아니므로 "인지"나 "확인"보다 "가설"로 표현한다.

현재 표시 기준:

```text
기준 측정에서 주문은 모두 성공했고 최종 재고도 기대값과 일치함. 다만 p95, p99 응답 시간이 높게 나타났고, 모든 요청이 같은 상품의 stocks 행을 차감하는 조건이었기 때문에 row-level lock 대기가 응답 지연에 영향을 줬을 것으로 가정함.
```

### 2. 개선 방법과 이유

적용한 개선 방법과 그 선택 이유를 함께 설명한다.

현재 표시 기준:

```text
기존 방식은 stocks 행을 비관적 락으로 조회한 뒤 재고를 검증하고 차감함. 개선 후에는 quantity >= 주문 수량 조건을 가진 UPDATE 한 문장으로 재고 검증과 차감을 처리함. 락을 없애는 것이 아니라, 재고 차감이 필요한 구간을 짧게 만들기 위한 선택임.
```

### 3. 정합성 검증

정합성 검증은 글보다 상태 요소로 보여준다.
성능이 개선되어도 초과 판매가 발생하면 실패한 개선이기 때문이다.

- 충분한 재고 조건: 주문 500건 성공, 최종 재고 500
- 재고 소진 조건: 성공 100건, 실패 100건
- 초과 판매: 0건
- 저장 주문 수: 성공 요청 수와 일치

### 4. 측정 한계

측정 한계는 해당 개선에서 실제로 남은 분석 한계를 짧게 적는다.
로컬 환경, k6 사용 같은 공통 설명은 상단 공통 조건과 원천 리포트 문서에서 다루고, 화면 하단에서는 반복하지 않는다.

현재 표시 기준:

```text
DB 락 대기 시간과 커넥션 풀 대기 시간을 별도 지표로 수집하지 못해, 병목 원인은 응답 시간 변화와 코드 흐름을 근거로 한 가설로 남아 있음.
```

## 확장 규칙

- 성능 개선이 완료될 때마다 `docs/performance/report.md`에 결과를 먼저 기록한다.
- `/report` 화면은 완료된 성능 개선만 탭으로 추가한다.
- 측정 조건이 다른 실험은 같은 차트에서 직접 비교하지 않는다.
- 각 탭의 상세 영역은 해당 성능 개선의 측정 조건과 결과를 독립적으로 보여준다.
- 예정된 성능 개선이나 다음 개선 후보는 `/report` 화면에 표시하지 않는다.
