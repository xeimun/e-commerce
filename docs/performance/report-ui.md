# 성능 리포트 UI 설계

이 문서는 프론트엔드 `/report` 화면에서 성능 측정 결과를 어떻게 보여줄지 정리한다.
실제 측정 수치와 개선 과정의 원천 자료는 `docs/performance/report.md`에 기록하고, 이 문서는 화면 정보 구조와 시각화 기준에 집중한다.

## 목적

- 멘토링에 참여하는 멘토와 멘티, 채용담당자가 성능 개선 성과를 빠르게 이해할 수 있게 한다.
- 성능 개선 결과를 단순 수치 나열이 아니라 측정, 병목 가설, 개선, 재측정 흐름으로 보여준다.
- 정합성 검증과 측정 한계를 함께 보여주어 결과의 신뢰도를 높인다.

## 대상 독자

- 멘토링에 참여하는 멘토
- 멘토링에 참여하는 멘티
- 채용담당자 또는 포트폴리오 검토자

## 데이터 출처

- 성능 개선 후보와 진행 상태: `docs/performance/plan.md`
- 실제 측정 결과와 해석: `docs/performance/report.md`
- 화면에는 완료된 성능 개선 결과만 노출한다.
- 다음 성능 개선 후보나 아직 수행하지 않은 항목은 `/report` 화면에 표시하지 않는다.

## 화면 구조

`/report` 화면은 상단 대시보드와 성능 개선별 상세 리포트로 구성한다.

```text
/report

전체 성능 개선 요약 대시보드
성능 개선별 탭
선택된 성능 개선 상세 리포트
```

### 상단 대시보드

상단 대시보드는 첫 화면에서 정량적 성과를 직관적으로 보여주는 영역이다.

- 대표 개선 지표
- 처리량 변화
- p95 응답 시간 변화
- 정합성 검증 요약
- 완료된 성능 개선 수

현재 첫 성능 개선의 대표 문장은 아래 기준으로 표시한다.

```text
초과 판매 0건을 유지하면서 p95 응답 시간을 1,610.89ms에서 1,342.18ms로 개선
```

### 성능 개선별 탭

상세 리포트는 성능 개선 단위로 탭을 나누어 보여준다.
서로 다른 성능 개선은 사용자 상황, 측정 조건, 병목 지점이 달라질 수 있으므로 하나의 차트에 무리하게 합치지 않는다.

- 탭에는 완료된 성능 개선만 표시한다.
- 탭 이름은 성능 개선 제목을 짧게 요약한다.
- 현재는 첫 번째 성능 개선 탭만 표시한다.
- 이후 성능 개선이 완료될 때마다 탭을 추가한다.
- 완료되지 않은 개선 후보명은 탭 예시나 비활성 탭으로도 노출하지 않는다.

## 상세 리포트 구성

선택된 탭의 상세 영역은 아래 순서로 배치한다.

1. 상황
2. 병목 가설
3. 개선 전후 수치 비교
4. 정합성 검증
5. 한계
6. 면접용 요약

다음 개선 후보는 상세 리포트에 표시하지 않는다.

## 차트 구성

차트는 전후 비교가 쉬운 구성을 우선한다.

### 처리량

- 전후 비교 막대 차트로 표시한다.
- 값 단위는 `건/초`로 표시한다.
- k6 setup 시간을 제외한 주문 생성 구간 기준 처리량을 사용한다.
- 개선 후 값이 커질수록 좋은 지표임을 시각적으로 드러낸다.

현재 데이터:

| 지표 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 처리량 | 76.97건/초 | 103.76건/초 |

### 응답 시간

- 평균, p95, p99를 grouped bar chart로 표시한다.
- 값 단위는 `ms`로 표시한다.
- 응답 시간은 낮을수록 좋은 지표이므로 색상과 라벨에서 처리량과 혼동되지 않게 한다.

현재 데이터:

| 지표 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 평균 응답 시간 | 1,179.77ms | 870.26ms |
| p95 응답 시간 | 1,610.89ms | 1,342.18ms |
| p99 응답 시간 | 1,630.56ms | 1,450.14ms |

### 정합성 검증

정합성 검증은 차트보다 상태 카드와 체크리스트를 우선한다.
성능 수치보다 초과 판매 방지와 실패 시 롤백이 더 중요한 기준이기 때문이다.

현재 데이터:

| 검증 항목 | 결과 |
| --- | --- |
| 충분한 재고 조건 | 주문 500건 성공, 실패 0건 |
| 최종 재고 | 기대 재고 500, 실제 재고 500 |
| 재고 소진 조건 | 주문 200건 중 성공 100건, 실패 100건 |
| 초과 판매 | 0건 |
| 재고 소진 저장 주문 | 성공 수와 같은 100건 |

## 한계 표시 방식

한계는 숨기지 않고 상세 리포트 하단에 표시한다.
단, 첫 화면의 핵심 성과를 가리지 않도록 보조 영역으로 배치한다.

현재 표시할 한계:

- 로컬 개발 장비와 Docker Compose 환경에서 측정했다.
- k6 setup 단계에서 장바구니를 준비하고, 주문 생성 구간만 커스텀 메트릭으로 비교했다.
- k6와 애플리케이션 서버가 같은 로컬 장비에서 실행되어 클라이언트와 서버 자원 사용이 완전히 분리되지는 않는다.
- DB 락 대기 시간과 커넥션 풀 대기 시간은 별도 지표로 수집하지 못했다.
- 각 조건은 단발 측정이므로 운영 처리량 보장이 아니라 같은 조건의 상대 비교 근거로 사용한다.

## 확장 규칙

- 성능 개선이 완료될 때마다 `docs/performance/report.md`에 결과를 먼저 기록한다.
- `/report` 화면은 완료된 성능 개선만 탭으로 추가한다.
- 측정 조건이 다른 실험은 같은 차트에서 직접 비교하지 않는다.
- 전체 대시보드는 여러 성능 개선 중 대표 성과만 요약한다.
- 각 탭의 상세 영역은 해당 성능 개선의 측정 조건과 결과를 독립적으로 보여준다.
- 예정된 성능 개선이나 다음 개선 후보는 `/report` 화면에 표시하지 않는다.
