# 성능 측정 및 개선 리포트

이 문서는 실제 성능 측정 결과, 병목 가설, 개선 내용, 재측정 결과를 기록한다. 성능 개선 후보와 우선순위는 `docs/performance/plan.md`에서 관리한다.

## 기록 원칙

- 측정 결과는 수치와 해석을 함께 기록한다.
- 개선 전후 조건이 다르면 직접 비교하지 않는다.
- 정합성 기준과 성능 기준을 분리해 기록한다.
- 로컬 측정 결과는 운영 성능 보장이 아니라 같은 조건에서의 상대 비교 근거로 사용한다.
- 면접에서 설명 가능한 성과 문장을 함께 남긴다.

## 용어 읽는 법

- `k6`: HTTP API에 부하를 걸어 응답 시간, 처리량, 실패율을 측정하는 성능 테스트 도구다. nGrinder처럼 성능 측정에 사용할 수 있지만, 스크립트를 JavaScript로 작성하고 CLI로 실행하는 방식이 가볍다.
- `VU`: Virtual User의 약자다. k6에서 동시에 요청을 보내는 가상 사용자 수를 뜻한다. 이번 측정의 `VU 100`은 주문을 동시에 시도하는 사용자를 100명으로 둔 조건이다.
- `처리량`: 일정 시간 동안 처리한 주문 수다. 이번 리포트에서는 k6 setup 시간을 제외하고 `주문 생성 구간의 전체 주문 수 / 주문 생성 구간 초`로 계산했다.
- `평균 응답 시간`: 모든 주문 생성 응답 시간을 더한 뒤 요청 수로 나눈 값이다.
- `p95 응답 시간`: 응답 시간을 빠른 순서로 세웠을 때 95% 지점의 값이다. 예를 들어 p95가 1,342ms라면 대부분의 요청이 1,342ms 안에 끝났고, 가장 느린 5%는 그보다 오래 걸렸다는 뜻이다.
- `p99 응답 시간`: 99% 지점의 값이다. 서비스에서 느린 꼬리 구간을 보는 지표라서 tail latency라고도 부른다.
- `초과 판매`: 실제 재고보다 더 많은 주문이 성공하는 정합성 오류다. 성능이 좋아져도 초과 판매가 발생하면 개선으로 볼 수 없다.

### 인기 상품 주문 생성과 재고 차감

#### 상황

한정판 굿즈 판매 시작 직후 여러 고객이 같은 인기 상품을 미리 장바구니에 담아두고 동시에 주문 생성 요청을 보내는 상황을 재현했다.
첫 개선 범위에서는 쿠폰 없는 단건 주문만 사용해 `stocks` hot row의 재고 차감 병목을 분리했다.

#### 문제

기존 주문 생성은 장바구니와 쿠폰 검증 후 `stocks` 행을 `PESSIMISTIC_WRITE`로 조회하고, 재고를 검증한 뒤 엔티티 수량을 차감했다.
비관적 락은 초과 판매를 막지만, 같은 상품에 주문이 몰리면 재고 행을 읽은 시점부터 주문 저장 전까지 뒤 요청이 대기할 수 있다.

#### 중심 CS 개념

- critical section 최소화

#### 보조 개념

- 트랜잭션 원자성
- row-level lock
- lock contention
- race condition
- lost update

#### 측정 조건

- 측정 일시: 2026-06-07
- 환경: 로컬 Windows, Spring Boot 3.5.x, PostgreSQL 17 Docker Compose, 서버 포트 8080
- 측정 도구: k6 v2.0.0
- 측정 스크립트: `k6/order-create-stock-reservation.js`
- 개선 전 비교 대상: 조건부 업데이트 적용 전 코드
- 개선 후 비교 대상: 조건부 업데이트 적용 코드
- 데이터 조건: 상품 `10001`, 고객별 장바구니 1개, 주문 수량 1개, 쿠폰 없음
- 부하 조건: k6 `shared-iterations`, VU 100
- 처리량 계산: `order_create_started_at`의 최소값부터 `order_create_finished_at`의 최대값까지를 주문 생성 구간으로 보고, 주문 수를 해당 시간으로 나누었다.
- 응답 시간 계산: k6 커스텀 Trend인 `order_create_duration`을 사용했다. 이 값은 주문 생성 API 응답 시간이며, setup 단계의 장바구니 준비 요청은 제외한다.

#### 기준 측정

충분한 재고 조건은 상품 재고를 1000개로 초기화하고 주문 생성 500건을 보냈다.

| 지표 | 기준 측정 |
| --- | ---: |
| 성공 요청 | 500건 |
| 실패 요청 | 0건 |
| 주문 생성 구간 | 6.50초 |
| 처리량 | 76.97건/초 |
| 평균 응답 시간 | 1,179.77ms |
| p95 응답 시간 | 1,610.89ms |
| p99 응답 시간 | 1,630.56ms |
| 최종 재고 | 500 |
| 기대 재고 | 500 |

#### 병목 가설

기준 측정에서 모든 주문은 성공했고 초과 판매도 없었지만, p95가 1.6초를 넘었다.
같은 상품의 `stocks` 행에 요청이 집중되면서 비관적 락을 얻은 트랜잭션만 재고 검증과 차감을 진행하고, 뒤 요청들은 row-level lock을 기다린 것으로 보았다.
특히 재고를 잠근 뒤 주문 상품 생성과 주문 저장 흐름이 이어져 락 보유 시간이 응답 지연에 영향을 준다고 판단했다.

#### 개선 내용

재고 차감 방식을 비관적 락 기반 read-check-write에서 조건부 업데이트로 변경했다.

```sql
update stocks
set quantity = quantity - :quantity
where product_id = :productId
  and quantity >= :quantity
```

이 방식은 PostgreSQL의 `UPDATE`가 필요한 row lock을 잡는 점은 동일하지만, 재고 검증과 차감을 하나의 DB 문장으로 처리한다.
주문 생성 서비스는 상품 상태와 할인 금액 스냅샷을 먼저 준비한 뒤 조건부 차감 쿼리를 실행하고, 쿼리 결과가 0건이면 `OUT_OF_STOCK`으로 실패시킨다.
여러 상품 주문에서는 상품별 주문 수량을 합산해 차감하며, 일부 차감 후 다른 상품이 실패해도 같은 트랜잭션에서 예외가 발생하므로 전체 변경이 롤백된다.

#### 결과 해석

충분한 재고 조건에서 주문 생성 p95 응답 시간은 1,610.89ms에서 1,342.18ms로 낮아졌다.
평균 응답 시간은 26.2% 감소했고, 주문 생성 구간 처리량은 76.97건/초에서 103.76건/초로 34.8% 증가했다.
p99도 11.1% 감소했지만 p95보다 개선 폭이 작다. 즉, 조건부 업데이트로 재고 차감 임계 구역은 줄었지만 가장 느린 꼬리 구간에는 주문 저장, 커넥션 풀, DB 대기 같은 다른 요인이 남아 있을 수 있다.

재고 소진 조건에서는 성공 100건, 실패 100건, 최종 재고 0을 유지하면서 응답 시간과 처리량이 함께 개선됐다.
이는 조건부 업데이트가 재고 부족 요청에서도 초과 판매 없이 빠르게 실패를 판정하는 데 도움이 됐다는 근거로 볼 수 있다.

#### 정합성 검증

- 충분한 재고 조건에서 주문 500건 모두 성공했고 최종 재고는 기대값 500과 일치했다.
- 재고 100개에 주문 200건, VU 100 조건을 주었을 때 성공 100건, 실패 100건, 최종 재고 0을 확인했다.
- 재고 소진 조건에서도 초과 판매는 0건이었다.
- 재고 소진 조건의 저장 주문 수는 100건으로 k6 성공 요청 수와 일치했다.
- 단위 테스트와 통합 테스트로 주문 생성 성공/실패, 재고 차감, 주문 저장 롤백, 결제 취소/만료 재고 복구 흐름을 검증했다.

#### 한계

- 로컬 개발 장비와 Docker Compose 환경의 단발 측정이라 운영 환경 성능으로 일반화할 수 없다.
- k6와 애플리케이션 서버가 같은 로컬 장비에서 실행되어 클라이언트와 서버 자원 사용이 완전히 분리되지는 않는다.
- DB 락 대기 시간, 커넥션 풀 대기 시간, 쿼리별 수행 시간은 별도 지표로 수집하지 못했다.
- setup 단계에서 장바구니를 미리 준비하므로 실제 사용자의 전체 흐름 성능이 아니라 주문 생성 API 구간 비교다.
- 더 신뢰도 높은 비교를 위해서는 반복 측정 평균, 표준편차, 독립 부하 발생기, 운영과 유사한 DB 설정이 필요하다.

#### 면접용 요약

기존 주문 생성 기능은 인기 상품에 주문이 몰릴 때 `stocks` 행을 비관적 락으로 잡고 재고 검증과 차감을 처리해 초과 판매는 막았지만, hot row 대기 때문에 p95 응답 시간이 커졌다.
재고 차감을 조건부 업데이트로 바꾸어 검증과 차감을 하나의 DB 문장으로 처리했고, k6 VU 100 측정에서 초과 판매 0건을 유지하면서 p95 응답 시간을 1,610.89ms에서 1,342.18ms로 낮추고 주문 생성 구간 처리량을 76.97건/초에서 103.76건/초로 개선했다.
