# 성능 측정 및 개선 리포트

이 문서는 실제 성능 측정 결과, 병목 가설, 개선 내용, 재측정 결과를 기록한다. 성능 개선 후보와 우선순위는 `docs/performance/plan.md`에서 관리한다.

## 기록 원칙

- 측정 결과는 수치와 해석을 함께 기록한다.
- 개선 전후 조건이 다르면 직접 비교하지 않는다.
- 정합성 기준과 성능 기준을 분리해 기록한다.
- 로컬 측정 결과는 운영 성능 보장이 아니라 같은 조건에서의 상대 비교 근거로 사용한다.
- 면접에서 설명 가능한 성과 문장을 함께 남긴다.

### 인기 상품 주문 생성과 재고 차감

#### 상황

한정판 굿즈 판매 시작 직후 여러 고객이 같은 인기 상품을 미리 장바구니에 담아두고 동시에 주문 생성 요청을 보내는 상황을 재현했다.
첫 개선 범위에서는 쿠폰 없는 단건 주문만 사용해 `stocks` hot row의 재고 차감 병목을 분리했다.

#### 문제

기존 주문 생성은 장바구니와 쿠폰 검증 후 `stocks` 행을 `PESSIMISTIC_WRITE`로 조회하고, 재고를 검증한 뒤 엔티티 수량을 차감했다.
비관적 락은 초과 판매를 막지만, 같은 상품에 주문이 몰리면 재고 행을 읽은 시점부터 주문 저장 전까지 뒤 요청이 대기할 수 있다.

#### 중심 CS 개념

- critical section 최소화

#### 보조 개념

- 트랜잭션 원자성
- row-level lock
- lock contention
- race condition
- lost update

#### 기준 측정

- 측정 일시: 2026-06-07
- 환경: 로컬 Windows, Spring Boot 3.5.x, PostgreSQL 17 Docker Compose, 서버 포트 8080
- 측정 도구: Node.js 내장 `fetch` 기반 HTTP 동시 요청 스크립트
- k6 상태: 로컬에 설치되어 있지 않아 이번 측정에서는 사용하지 못했다.
- 데이터 조건: 상품 `10001`, 재고 `1000`, 고객별 장바구니 1개, 주문 수량 1개, 쿠폰 없음
- 부하 조건: 주문 생성 500건, 동시성 100

| 지표 | 기준 측정 |
| --- | ---: |
| 성공 요청 | 500건 |
| 실패 요청 | 0건 |
| 처리량 | 5,647.27건/분 |
| 평균 응답 시간 | 963.63ms |
| p95 응답 시간 | 1,097.51ms |
| p99 응답 시간 | 1,117.01ms |
| 최종 재고 | 500 |
| 기대 재고 | 500 |

#### 병목 가설

기준 측정에서 모든 주문은 성공했고 초과 판매는 없었지만, p95가 1초를 넘었다.
같은 상품의 `stocks` 행에 요청이 집중되면서 비관적 락을 얻은 트랜잭션만 재고 검증과 차감을 진행하고, 뒤 요청들은 row-level lock을 기다린 것으로 보았다.
특히 재고를 잠근 뒤 할인 계산, 주문 상품 생성, 주문 저장 흐름이 이어져 락 보유 시간이 응답 지연에 영향을 준다고 판단했다.

#### 개선 내용

재고 차감 방식을 비관적 락 기반 read-check-write에서 조건부 업데이트로 변경했다.

```sql
update stocks
set quantity = quantity - :quantity
where product_id = :productId
  and quantity >= :quantity
```

이 방식은 PostgreSQL의 `UPDATE`가 필요한 row lock을 잡는 점은 동일하지만, 재고 검증과 차감을 하나의 DB 문장으로 처리한다.
주문 생성 서비스는 상품 상태와 할인 금액 스냅샷을 먼저 준비한 뒤 조건부 차감 쿼리를 실행하고, 쿼리 결과가 0건이면 `OUT_OF_STOCK`으로 실패시킨다.
여러 상품 주문에서는 상품별 주문 수량을 합산해 차감하며, 일부 차감 후 다른 상품이 실패해도 같은 트랜잭션에서 예외가 발생하므로 전체 변경이 롤백된다.

#### 재측정

개선 후 같은 상품, 같은 재고, 같은 고객 수, 같은 동시성으로 재측정했다.
기동 직후 첫 고부하 재측정은 p95가 1,731.29ms로 튀었고, 직후 동일 조건 반복 측정에서 아래 결과를 얻었다.
로컬 단발 측정 노이즈가 있으므로 최종 수치는 운영 성능 보장이 아니라 같은 조건 반복 측정의 비교 근거로만 사용한다.

| 지표 | 기준 측정 | 개선 후 |
| --- | ---: | ---: |
| 성공 요청 | 500건 | 500건 |
| 실패 요청 | 0건 | 0건 |
| 처리량 | 5,647.27건/분 | 7,114.73건/분 |
| 평균 응답 시간 | 963.63ms | 763.62ms |
| p95 응답 시간 | 1,097.51ms | 962.91ms |
| p99 응답 시간 | 1,117.01ms | 1,077.76ms |
| 최종 재고 | 500 | 500 |
| 기대 재고 | 500 | 500 |

보조 확인으로 주문 생성 200건, 동시성 40 조건도 측정했다.

| 지표 | 기준 측정 | 개선 후 |
| --- | ---: | ---: |
| 처리량 | 4,104.25건/분 | 5,852.71건/분 |
| 평균 응답 시간 | 536.59ms | 345.65ms |
| p95 응답 시간 | 759.06ms | 503.33ms |
| p99 응답 시간 | 777.22ms | 594.35ms |
| 성공 요청 | 200건 | 200건 |
| 실패 요청 | 0건 | 0건 |

#### 결과 해석

동시성 100 조건에서 p95는 1,097.51ms에서 962.91ms로 낮아져 1차 목표인 1초 이하에 들어왔다.
처리량은 5,647.27건/분에서 7,114.73건/분으로 증가했다.
p99도 1,117.01ms에서 1,077.76ms로 낮아졌지만 개선 폭은 p95보다 작아, tail latency는 다음 개선에서 트랜잭션 범위와 주문 저장 비용까지 함께 봐야 한다.

#### 정합성 검증

- 충분한 재고 조건에서 주문 500건 모두 성공했고 최종 재고는 기대값 500과 일치했다.
- 재고 100개에 주문 200건, 동시성 100 조건을 주었을 때 성공 100건, 실패 100건, 최종 재고 0을 확인했다.
- 재고 소진 조건의 실패 응답은 `ORDER_VALIDATION_FAILED`였고, 샘플 실패 고객의 주문 목록은 빈 배열이었다.
- 단위 테스트와 통합 테스트로 주문 생성 성공/실패, 재고 차감, 주문 저장 롤백, 결제 취소/만료 재고 복구 흐름을 검증했다.

#### 한계

- k6가 설치되어 있지 않아 Node.js 내장 `fetch`로 측정했다.
- 로컬 개발 장비와 Docker Compose 환경의 단발 측정이라 운영 환경 성능으로 일반화할 수 없다.
- 부하 테스트 데이터가 DB에 누적될수록 주문 저장 비용이 달라질 수 있다.
- DB 락 대기 시간과 커넥션 풀 대기 시간은 별도 지표로 수집하지 못했다.
- 기동 직후 첫 고부하 재측정 값이 튀어, 더 신뢰도 높은 비교를 위해서는 측정 전 데이터 초기화와 반복 측정 평균이 필요하다.

#### 다음 방향

다음 개선은 주문 생성 트랜잭션 범위와 락 보유 시간을 더 세분화해 본다.
조건부 업데이트 이후에도 `orders`, `order_items` 저장과 쿠폰 예약이 같은 트랜잭션에 남아 있으므로 DB 쿼리 수, 트랜잭션 수행 시간, 커넥션 풀 대기 가능성을 함께 확인한다.

#### 면접용 요약

인기 상품 주문 집중 상황에서 비관적 락 기반 재고 차감을 조건부 업데이트로 바꾸어 초과 판매 0건을 유지했다.
로컬 동시성 100 측정에서 주문 생성 p95 응답 시간을 1,097.51ms에서 962.91ms로 낮추고 처리량을 5,647.27건/분에서 7,114.73건/분으로 개선했다.
