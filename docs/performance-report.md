# 성능 측정 및 개선 기록

이 문서는 기준 성능 측정, 병목 가설, 개선 내용, 재측정 결과를 정리한다.
아직 성능 측정 단계에 들어가지 않은 항목은 향후 측정 후보로만 기록한다.

## 성능 개선 방향

성능 개선은 실제 운영 환경이 아니라 로컬 개발 환경에서 진행한다.
따라서 절대적인 수치를 운영 성능으로 주장하지 않고, 같은 로컬 조건에서 개선 전후의 상대적인 변화를 비교한다.

### 핵심 목표

한정판 굿즈 드롭 오픈 직후 인기 상품 주문이 몰리는 상황을 가정한다.
목표는 `POST /api/v1/orders` 주문 생성 요청에서 재고와 쿠폰 정합성을 깨지 않으면서 분당 100건 이상의 주문 생성 부하를 처리하는 것이다.

### 성공 기준

성공 기준은 정합성 기준과 성능 기준을 분리한다.

정합성 기준은 반드시 만족해야 한다.

- 초과 판매 0건
- 쿠폰 중복 사용 0건
- 주문 생성 실패 시 재고 차감, 쿠폰 예약, 주문 저장 흔적 0건
- 서버 내부 오류 0건

성능 기준은 개선 전후 비교 대상으로 둔다.

- 주문 생성 처리량 100건/분 이상
- 주문 생성 p95 응답 시간 1초 이하를 1차 목표로 설정
- p99 응답 시간, 실패율, DB 락 대기 시간, 커넥션 풀 대기 시간은 관찰 지표로 기록

### 로컬 측정 한계

로컬 측정은 운영 환경과 하드웨어, 네트워크, DB 설정이 다르다.
따라서 이 문서의 성능 수치는 운영 처리량 보장이 아니라 병목 분석과 개선 효과 비교를 위한 근거로 사용한다.

- 같은 장비, 같은 DB, 같은 애플리케이션 설정에서 개선 전후를 비교한다.
- 부하 테스트 전 데이터 상태를 재현 가능하게 준비한다.
- 평균 응답 시간보다 p95, p99, 실패율, 정합성 실패 여부를 우선 기록한다.
- 외부 결제 API, 인증 서버, CDN 같은 운영 의존성은 첫 성능 측정 범위에서 제외한다.

## 성능 개선 절차

성능 개선은 아래 순서로만 진행한다.
여러 개선을 한 번에 적용하면 어떤 변경이 효과를 만들었는지 설명하기 어렵기 때문이다.

```text
상황 가정 -> 기준 데이터 준비 -> 기준 성능 측정 -> 병목 가설 수립 -> 개선안 1개 적용 -> 재측정 -> 결과 비교 -> 문서화
```

### 1. 상황 가정

성능 실험마다 어떤 사용 상황을 재현하는지 먼저 정한다.

- 한정판 상품 오픈 직후 특정 상품에 주문이 집중된다.
- 여러 고객이 미리 장바구니에 담아둔 상태에서 동시에 주문 생성 요청을 보낸다.
- 재고가 충분한 경우와 재고가 소진되는 경우를 나누어 본다.
- 쿠폰 없는 주문으로 재고 병목을 먼저 측정하고, 이후 쿠폰 포함 주문으로 확장한다.
- 결제 대기 만료 주문이 쌓인 상태에서 신규 주문이 들어오는 상황을 별도 실험으로 분리한다.

### 2. 기준 데이터 준비

부하 테스트 전 동일한 조건을 재현할 수 있도록 데이터를 준비한다.

- 인기 상품 1개와 충분한 재고
- 고객별 장바구니와 주문 대상 장바구니 상품
- 쿠폰 포함 실험에서는 고객별 발급 쿠폰
- 만료 처리 실험에서는 만료된 `PAYMENT_PENDING` 주문

### 3. 기준 성능 측정

현재 구현을 변경하지 않은 상태에서 먼저 측정한다.

- 처리량
- 평균 응답 시간
- p95, p99 응답 시간
- 성공/실패 요청 수
- 초과 판매 여부
- 쿠폰 중복 사용 여부
- DB 락 대기 또는 커넥션 풀 대기 가능성

### 4. 병목 가설 수립

측정 결과를 보고 병목 원인을 추정한다.

- 같은 상품의 `stocks` 행에 주문이 몰려 row-level lock 대기가 발생한다.
- 주문 생성 트랜잭션 안에서 재고 락을 보유하는 시간이 길다.
- 쿠폰 포함 주문에서 `issued_coupons` 행 락이 추가 경합을 만든다.
- 만료 주문 배치가 재고 복구 과정에서 신규 주문과 같은 재고 행을 두고 경합한다.
- 조회 API에서 연관 데이터 로딩이나 정렬 비용이 증가한다.

### 5. 개선안 1개 적용

개선은 한 번에 하나씩 적용한다.
적용 전에는 어떤 CS 개념을 활용하는지, 어떤 지표가 좋아질 것으로 예상하는지 기록한다.

### 6. 재측정과 결과 비교

개선 전과 같은 조건으로 재측정한다.
결과는 수치와 함께 해석을 남긴다.

- 어떤 지표가 좋아졌는지
- 어떤 지표가 악화되었는지
- 정합성 기준은 계속 만족하는지
- 개선안의 부작용이나 운영상 주의점은 무엇인지

## 문제별 성능 개선 후보

### 1. 인기 상품 주문 생성과 재고 차감

#### 실무 상황

한정판 굿즈 판매 시작 직후 많은 고객이 같은 상품을 주문한다.
현재 구현은 주문 생성 시 `stocks` 행을 비관적 락으로 잠근 뒤 재고를 검증하고 차감한다.

#### 문제

비관적 락은 초과 판매를 막는 데 효과적이지만, 같은 상품에 요청이 몰리면 하나의 재고 행을 기준으로 주문 생성이 순서대로 처리된다.
이때 뒤 요청들은 락을 기다리며 p95, p99 응답 시간이 증가할 수 있다.

#### 활용할 CS 개념

- 트랜잭션 원자성
- row-level lock
- race condition
- lost update
- critical section
- 큐잉과 대기 시간

#### 비교할 개선안

| 개선안 | 기대 효과 | 주의점 |
| --- | --- | --- |
| 비관적 락 유지 | 초과 판매 방지가 직관적이고 구현이 안정적이다. | 인기 상품 hot row에서 락 대기가 증가할 수 있다. |
| 조건부 재고 차감 쿼리 | `quantity >= 주문 수량` 조건으로 DB에서 원자적으로 차감해 락 보유 시간을 줄일 수 있다. | 주문 상품이 여러 개인 경우 전체 성공/실패 처리와 금액 스냅샷 흐름을 신중히 설계해야 한다. |
| 낙관적 락 | 충돌이 적은 상품에서는 락 대기보다 효율적일 수 있다. | 인기 상품처럼 충돌이 많은 상황에서는 재시도 비용이 커질 수 있다. |
| 트랜잭션 범위 축소 | 재고 락을 잡고 있는 시간을 줄여 대기 시간을 낮출 수 있다. | 락 밖에서 검증한 값이 락 이후에도 유효한지 다시 확인해야 한다. |

#### 측정 지표

- 주문 생성 처리량
- p95, p99 응답 시간
- 초과 판매 여부
- 재고 부족 실패 수
- DB 락 대기 시간

#### 이력서 성과 후보

```text
인기 상품 주문 집중 상황에서 재고 차감 동시성 병목을 분석하고,
DB row-level lock과 조건부 업데이트 방식을 비교해 초과 판매 0건을 유지하면서 주문 생성 응답 시간을 개선
```

### 2. 주문 생성 트랜잭션 범위와 락 보유 시간

#### 실무 상황

주문 생성은 장바구니 검증, 상품 상태 검증, 재고 차감, 쿠폰 검증, 할인 계산, 주문 저장을 하나의 흐름으로 처리한다.
이 중 일부 작업은 재고 락을 잡기 전에 처리할 수 있고, 일부 작업은 락 이후 최신 데이터로 다시 확인해야 한다.

#### 문제

트랜잭션이 길고 락을 잡은 상태에서 수행하는 작업이 많으면 같은 상품을 주문하는 뒤 요청들의 대기 시간이 증가한다.

#### 활용할 CS 개념

- critical section 최소화
- 트랜잭션 경계
- lock hold time
- DB round trip
- 영속성 컨텍스트와 데이터 신선도

#### 개선 후보

- 락이 필요 없는 요청 형식 검증과 중복 ID 검증을 락 전에 끝낸다.
- 재고 락 이후에는 반드시 최신 재고로 검증하고 빠르게 차감한다.
- 주문 저장 전 필요한 조회 수를 줄인다.
- 필요하면 주문 생성 경로 전용 조회 쿼리나 DTO projection을 검토한다.

#### 측정 지표

- 주문 생성 p95, p99 응답 시간
- 재고 락 대기 시간
- 트랜잭션 수행 시간
- DB 쿼리 수

#### 이력서 성과 후보

```text
주문 생성 트랜잭션에서 재고 락 보유 시간이 길어지는 문제를 분석하고,
검증 순서와 트랜잭션 경계를 조정해 동시 주문 상황의 p95 응답 시간을 개선
```

### 3. 쿠폰 포함 주문의 중복 사용 방지와 락 경합

#### 실무 상황

고객이 발급받은 쿠폰을 주문에 적용한다.
같은 쿠폰으로 동시에 여러 주문 생성 요청이 들어오면 쿠폰이 중복 예약되거나 중복 사용될 위험이 있다.

#### 문제

쿠폰 행을 비관적 락으로 잠그면 중복 사용은 막을 수 있지만, 쿠폰 포함 주문이 많아질수록 재고 락 외에 쿠폰 락도 응답 시간에 영향을 줄 수 있다.

#### 활용할 CS 개념

- 상태 전이
- 동시성 제어
- unique constraint
- idempotency
- deadlock과 락 획득 순서

#### 비교할 개선안

| 개선안 | 기대 효과 | 주의점 |
| --- | --- | --- |
| 발급 쿠폰 행 비관적 락 | 쿠폰 중복 예약을 직관적으로 차단한다. | 쿠폰 포함 주문에서 락 경합이 추가될 수 있다. |
| 상태 조건부 업데이트 | `status = AVAILABLE` 조건으로 예약 성공 여부를 DB 갱신 결과로 판단할 수 있다. | 실패 원인 메시지를 세분화하려면 추가 조회가 필요할 수 있다. |
| Idempotency key | 사용자 중복 클릭이나 클라이언트 재시도에 강해진다. | 첫 성능 개선 범위보다 API 계약과 저장 구조가 커질 수 있다. |

#### 측정 지표

- 쿠폰 포함 주문 p95, p99 응답 시간
- 쿠폰 중복 사용 여부
- 쿠폰 예약 실패 수
- deadlock 또는 lock timeout 발생 여부

#### 이력서 성과 후보

```text
쿠폰 포함 주문에서 발급 쿠폰 상태 전이와 동시성 제어를 검증하고,
쿠폰 중복 사용 0건을 유지하면서 재고 락과 쿠폰 락의 성능 영향을 분리 측정
```

### 4. 결제 대기 만료 배치와 신규 주문 경합

#### 실무 상황

결제 대기 주문은 10분 후 만료된다.
만료 처리는 주문을 취소하고 예약된 재고와 쿠폰을 복구한다.

#### 문제

만료 주문이 많이 쌓이면 스케줄러가 여러 주문을 한 번에 처리하면서 주문 행과 재고 행을 잠근다.
이때 신규 주문 생성도 같은 재고 행을 잠그려고 하면 사용자 요청 응답 시간이 증가할 수 있다.

#### 활용할 CS 개념

- 배치 처리
- 인덱스
- chunking
- lock contention
- foreground 작업과 background 작업 분리

#### 개선 후보

- `orders(status, expires_at)` 인덱스가 만료 대상 조회에 사용되는지 실행 계획으로 확인한다.
- 만료 주문을 한 번에 모두 처리하지 않고 일정 건수 단위로 처리한다.
- 만료 주문 처리 중 재고 복구 대상 상품을 합산해 DB 수정 횟수를 줄인다.
- 신규 주문이 몰리는 시간대와 만료 배치 실행 시점을 분리할 수 있는지 검토한다.

#### 측정 지표

- 만료 처리 건수
- 만료 처리 수행 시간
- 만료 처리 중 신규 주문 p95, p99 응답 시간
- 재고 복구 중 락 대기 시간

#### 이력서 성과 후보

```text
결제 대기 만료 주문이 대량 발생하는 상황에서 배치 처리와 신규 주문의 재고 락 경합을 분석하고,
인덱스와 청크 처리 전략으로 사용자 주문 요청에 주는 영향을 완화
```

### 5. 상품/주문 조회 성능

#### 실무 상황

사용자는 상품 목록, 주문 목록, 주문 상세를 반복 조회한다.
주문 데이터가 늘어나면 단순 조회 API도 응답 시간과 DB 부하에 영향을 준다.

#### 문제

연관 데이터를 필요한 것보다 많이 로딩하거나, 정렬과 페이징에 적합한 인덱스가 없으면 조회 성능이 떨어질 수 있다.

#### 활용할 CS 개념

- N+1 문제
- 인덱스
- 실행 계획
- projection
- pagination

#### 개선 후보

- EntityGraph와 fetch join이 실제 쿼리 수를 줄이는지 확인한다.
- 목록 조회는 필요한 필드만 반환하는 projection을 검토한다.
- 주문 목록은 `customer_id`, `id` 또는 생성 시각 기준 인덱스를 검토한다.
- 큰 목록은 offset pagination과 keyset pagination의 차이를 비교한다.

#### 측정 지표

- 조회 API 평균, p95 응답 시간
- SQL 쿼리 수
- 실행 계획
- DB scan 범위

#### 현재 우선순위

조회 성능은 주문 생성 성능 개선 이후 보조 개선 후보로 둔다.
이 프로젝트의 핵심 성과는 먼저 주문 생성 정합성과 처리량 개선으로 만든다.

## 향후 측정 후보

### 장바구니 상품 추가 동시성 정합성

#### 배경

장바구니에 이미 같은 상품이 있는 상태에서 `POST /api/v1/cart/items` 요청이 동시에 들어오면, 현재 구현의 읽기-계산-쓰기 흐름에서 lost update가 발생할 수 있다.
예를 들어 기존 수량이 1이고 동시에 1개 추가 요청 2건이 들어오면 기대 수량은 3이지만, 두 트랜잭션이 같은 기존 수량을 읽으면 최종 수량이 2로 남을 수 있다.

#### 측정 가치

- 더블 클릭, 모바일 재시도, 클라이언트 중복 요청 같은 일반적인 상황에서 수량 증가 규칙이 유지되는지 확인할 수 있다.
- 단순 평균 응답 시간보다 동시성 환경에서의 정합성 실패율을 함께 측정할 수 있다.
- 이후 주문 생성과 재고 차감 동시성 테스트를 설계하기 위한 작은 선행 사례로 활용할 수 있다.

#### 측정 아이디어

- 기준 상태: 고객 1명의 장바구니에 특정 상품 수량 1개가 이미 담겨 있음
- 부하 조건: 같은 고객, 같은 상품으로 `POST /api/v1/cart/items` 추가 요청을 동시에 N건 전송
- 기대 결과: 최종 장바구니 수량이 `기존 수량 + 성공 요청 수량 합계`와 일치
- 관찰 지표: 최종 수량 정합성, 실패율, 응답 시간, 처리량, DB 락 대기 또는 충돌 발생 여부

#### 개선 후보

- 대상 `cart_items` 행에 비관적 락 적용
- JPA `@Version` 기반 낙관적 락 적용
- DB의 원자적 수량 증가 쿼리 사용

#### 현재 상태

- 아직 개선을 적용하지 않는다.
- 장바구니 기능 PR의 코드 리뷰에서 발견된 향후 측정 및 개선 후보로 보관한다.
