# 학습 노트

이 문서는 구현 중 등장한 백엔드/CS 개념을 이해하기 쉽게 정리한다.
모든 대화 내용을 기록하지 않고, 프로젝트에 실제로 적용되었거나 이후 면접 설명에 도움이 되는 개념만 남긴다.

## DB 마이그레이션과 Flyway

### 한 줄 정리

DB 마이그레이션은 DB 스키마 변경 이력을 버전이 있는 파일로 관리하는 방식이고, Flyway는 이를 자동으로 적용해주는 도구다.

### 왜 필요했나

상품, 재고, 장바구니, 주문, 쿠폰 테이블은 구현 과정에서 계속 변경될 수 있다.
스키마 변경 이력을 코드와 함께 관리하지 않으면 어떤 변경이 언제 적용됐는지 추적하기 어렵다.

### 핵심 개념

- 마이그레이션: 테이블 생성, 컬럼 추가, 인덱스 추가 같은 DB 스키마 변경을 관리하는 방식
- Versioned Migration: `V1__init.sql`, `V2__add_order_table.sql`처럼 순서가 있는 변경 파일
- Schema History: 어떤 마이그레이션이 적용됐는지 기록하는 Flyway 관리 테이블

### 프로젝트 적용

- DB 스키마 변경은 Flyway SQL 파일로 관리한다.
- 테이블 생성, 컬럼 변경, 인덱스 추가는 마이그레이션 파일에 기록한다.
- 성능 개선 단계에서 인덱스를 추가할 때도 Flyway로 변경 이력을 남긴다.

### 추가로 공부할 것

- Flyway baseline
- repeatable migration
- 운영 DB 마이그레이션 주의점

## JPA ddl-auto validate

### 한 줄 정리

`ddl-auto=validate`는 JPA 엔티티와 실제 DB 스키마가 일치하는지 애플리케이션 시작 시 검증하는 설정이다.

### 왜 필요했나

DB 스키마는 Flyway로 관리하기로 했기 때문에 JPA가 테이블을 자동 생성하거나 수정하지 않도록 해야 한다.
대신 엔티티와 DB 스키마가 어긋났는지는 빠르게 확인할 필요가 있다.

### 핵심 개념

- `create`: 애플리케이션 실행 시 테이블을 새로 생성한다.
- `update`: 엔티티 기준으로 DB 스키마를 자동 변경하려고 시도한다.
- `validate`: 엔티티와 DB 스키마가 일치하는지 검증만 한다.
- `none`: JPA의 스키마 관련 동작을 사용하지 않는다.

### 프로젝트 적용

- 테이블 생성과 변경은 Flyway가 담당한다.
- JPA는 `ddl-auto=validate`로 스키마 일치 여부만 확인한다.
- 엔티티 변경 후 마이그레이션 SQL을 작성하지 않으면 애플리케이션 시작 시 문제를 발견할 수 있다.

### 추가로 공부할 것

- Hibernate DDL auto 옵션
- 운영 환경에서 `ddl-auto=update`를 피하는 이유
- 엔티티와 스키마 불일치 사례

## API 버전 관리

### 한 줄 정리

API 버전 관리는 요청/응답 형식이 크게 바뀌어도 기존 클라이언트를 보호하기 위해 API 경로 또는 헤더에 버전을 나누는 방식이다.

### 왜 필요했나

주문 생성 API는 이후 배송지, 결제 수단, 인증 정보 등이 추가되면서 요청/응답 형식이 바뀔 수 있다.
처음부터 API를 클라이언트와 서버 사이의 계약으로 보고 버전 관리를 적용하기로 했다.

### 핵심 개념

- URI versioning: `/api/v1/orders`, `/api/v2/orders`처럼 경로에 버전을 포함하는 방식
- Header versioning: 요청 헤더로 API 버전을 전달하는 방식
- 하위 호환성: 기존 클라이언트가 깨지지 않도록 변경을 관리하는 것
- API 계약: 서버와 클라이언트가 합의한 요청/응답 형식

### 프로젝트 적용

- 모든 API 경로는 `/api/v1`로 시작한다.
- 첫 버전은 URI versioning을 사용한다.
- API 요청/응답 형식이 크게 변경되면 이후 `/api/v2` 도입을 검토한다.

### 추가로 공부할 것

- API backward compatibility
- URI versioning과 header versioning 비교
- REST API 설계 원칙

## 재고 예약

### 한 줄 정리

재고 예약은 사용자가 주문을 생성해 결제 단계에 들어갔을 때 재고를 미리 차감해 일정 시간 동안 확보하는 방식이다.

### 왜 필요했나

결제 직전에 재고가 사라지면 사용자 경험이 좋지 않다.
주문 생성 시 재고를 예약 차감하면 사용자가 결제 대기 상태에 있는 동안 해당 재고를 확보할 수 있다.

### 핵심 개념

- 재고 차감 시점: 주문 생성 시점과 결제 성공 시점 중 언제 재고를 줄일지 결정해야 한다.
- 재고 정합성: 동시에 여러 주문이 들어와도 실제 재고보다 많이 판매되지 않도록 보장해야 한다.
- 보상 처리: 결제 취소 또는 만료 시 예약 차감한 재고를 복구해야 한다.

### 프로젝트 적용

- 주문 생성 시 상품 상태와 재고를 검증한다.
- 주문 생성 성공 시 재고를 즉시 차감하고 주문 상태를 `PAYMENT_PENDING`으로 만든다.
- 결제 취소 또는 결제 대기 만료 시 재고를 복구한다.
- 결제 성공 시 주문 상태를 `COMPLETED`로 변경한다.

### 추가로 공부할 것

- 트랜잭션
- 동시성 제어
- 비관적 락
- 낙관적 락
- 조건부 업데이트

## 결제 대기 만료와 스케줄러

### 한 줄 정리

결제 대기 만료는 결제가 완료되지 않은 주문을 일정 시간이 지난 뒤 자동 취소하는 정책이고, 스케줄러는 이 작업을 주기적으로 실행하는 방식이다.

### 왜 필요했나

주문 생성 시 재고를 예약 차감하기 때문에 결제가 완료되지 않은 주문이 계속 남으면 재고가 불필요하게 묶인다.
사용자가 결제 화면을 닫거나 결제를 진행하지 않는 상황을 처리해야 한다.

### 핵심 개념

- 결제 대기 시간: 사용자가 결제를 완료할 수 있는 제한 시간
- 자동 만료 처리: 시간이 지난 결제 대기 주문을 시스템이 취소하는 처리
- 스케줄러: 특정 작업을 일정 주기마다 실행하는 기능
- 복구 처리: 만료된 주문의 재고와 쿠폰 예약 상태를 되돌리는 작업

### 프로젝트 적용

- 결제 대기 주문의 유효 시간은 10분이다.
- Spring `@Scheduled`로 스케줄러를 등록하고, 1분마다 만료된 `PAYMENT_PENDING` 주문을 찾는다.
- 만료된 주문은 `CANCELED`로 변경한다.
- 만료 주문 조회 시 주문 행을 비관적 락으로 잠가 결제 성공/취소 요청과 중복 처리되지 않게 한다.
- 만료 취소 시 주문 상품 수량을 상품별로 합산해 재고를 복구한다.
- 예약된 쿠폰은 고객 보유 쿠폰 기능 구현 후 `AVAILABLE` 상태로 되돌린다.
- 결제 성공 API에서도 만료 여부를 한 번 더 검증한다.

### 추가로 공부할 것

- Spring `@Scheduled`
- 배치 처리
- 스케줄러 중복 실행 문제
- 분산 환경에서 스케줄러 운영 방식

## 금액 표현과 BigDecimal

### 한 줄 정리

`BigDecimal`은 십진수 기반 숫자를 정확하게 다룰 수 있어 금액처럼 오차가 없어야 하는 값에 적합하다.

### 왜 필요했나

이 프로젝트는 상품 가격, 상품 즉시 할인, 쿠폰 할인, 최종 결제 금액을 계산하고 주문 당시 금액으로 저장해야 한다.
금액 계산에서 작은 오차가 발생하면 결제 금액과 주문 기록의 신뢰성이 떨어질 수 있다.

### 핵심 개념

- `double`: 이진 부동소수점 방식이라 일부 십진수를 정확히 표현하지 못한다.
- `long`: 원화처럼 최소 화폐 단위가 정수일 때 단순하게 사용할 수 있다.
- `BigDecimal`: 십진수 연산을 정확히 표현할 수 있어 가격, 할인, 정산 금액에 자주 사용한다.
- scale: 소수점 아래 자리수다. 이 프로젝트의 DB 금액 컬럼은 `numeric(19, 2)`로 시작한다.

### 프로젝트 적용

- 상품 가격은 `BigDecimal`로 표현한다.
- DB 금액 컬럼은 `numeric(19, 2)`를 사용한다.
- 이후 주문 원금액, 할인 금액, 최종 결제 금액도 같은 방식으로 확장한다.

### 추가로 공부할 것

- `BigDecimal` 생성 시 문자열 생성자와 `valueOf` 차이
- `BigDecimal` 비교에서 `equals`와 `compareTo` 차이
- 반올림 정책과 `RoundingMode`

## JPA EntityGraph

### 한 줄 정리

`EntityGraph`는 JPA 조회 시 연관 엔티티를 함께 가져오도록 지정해 지연 로딩으로 인한 추가 쿼리를 줄이는 방법이다.

### 왜 필요했나

장바구니 조회 응답에는 장바구니 상품뿐 아니라 상품명, 가격, 판매 상태, 현재 재고가 함께 필요하다.
장바구니 상품마다 상품과 재고를 따로 조회하면 상품 수가 늘어날수록 쿼리가 증가할 수 있다.

### 핵심 개념

- Lazy Loading: 연관 객체를 실제 사용할 때 조회하는 방식
- N+1 문제: 목록 1번 조회 후 각 항목의 연관 데이터를 다시 조회해 쿼리가 많이 발생하는 문제
- EntityGraph: 특정 조회에서 함께 로딩할 연관 경로를 명시하는 방식

### 프로젝트 적용

- `CartRepository.findByCustomerId`에서 `items`, `items.product`, `items.product.stock`을 함께 조회한다.
- 장바구니 조회, 수정, 삭제에서 고객 소유 장바구니와 상품/재고 정보를 한 번의 서비스 흐름에서 검증한다.

### 추가로 공부할 것

- fetch join과 EntityGraph 비교
- 컬렉션 fetch 시 페이징 주의점
- Hibernate batch size

## 비관적 락과 재고 예약

### 한 줄 정리

비관적 락은 동시에 같은 데이터를 수정할 가능성이 높다고 보고, 먼저 DB 행을 잠근 뒤 읽고 수정하는 동시성 제어 방식이다.

### 왜 필요했나

주문 생성은 현재 재고를 확인한 뒤 바로 차감한다.
같은 상품에 주문이 동시에 들어오면 두 요청이 같은 재고 수량을 보고 모두 성공하는 초과 판매 문제가 생길 수 있다.

### 핵심 개념

- 트랜잭션: 재고 검증, 재고 차감, 주문 저장을 하나의 작업 단위로 묶는다.
- 비관적 락: 수정 대상 행을 잠가 다른 트랜잭션이 동시에 수정하지 못하게 한다.
- 락 대기: 같은 재고 행을 원하는 주문이 많으면 뒤의 트랜잭션은 앞의 트랜잭션이 끝날 때까지 기다린다.
- 롤백: 검증 실패나 예외가 발생하면 같은 트랜잭션 안의 변경을 취소한다.

### 프로젝트 적용

- 주문 생성 시 선택된 장바구니 상품의 `stocks` 행을 `PESSIMISTIC_WRITE`로 잠근다.
- 잠근 재고 수량으로 상품 상태와 재고를 다시 검증한다.
- 검증이 모두 통과하면 재고를 차감하고 `PAYMENT_PENDING` 주문을 저장한다.
- 검증 실패 시 주문을 저장하지 않고 재고도 차감하지 않는다.
- 주문 생성 경로에서는 장바구니 조회 시 `Stock`을 직접 가져오지 않는 전용 조회를 사용하고, 비관적 락 조회 후 `refresh`로 최신 재고 수량을 다시 읽는다. 이미 영속성 컨텍스트에 올라온 `Stock`이 있으면 락 조회 후에도 오래된 수량을 사용할 위험이 있기 때문이다.

### 추가로 공부할 것

- PostgreSQL `select for update`
- 낙관적 락과 재시도 정책
- 조건부 업데이트 방식의 재고 차감
- 락 대기 시간과 처리량의 관계

## Spring 트랜잭션 롤백 규칙

### 한 줄 정리

Spring의 `@Transactional`은 기본적으로 런타임 예외가 발생하면 트랜잭션을 롤백하고, `noRollbackFor`를 사용하면 특정 예외에서는 변경을 커밋할 수 있다.

### 왜 필요했나

만료된 결제 대기 주문에 결제 성공 API가 호출되면 실패 응답을 반환해야 하지만, 동시에 주문 취소와 재고 복구는 DB에 남아야 한다.
일반적인 런타임 예외를 그대로 던지면 취소와 재고 복구도 함께 롤백된다.

### 핵심 개념

- 트랜잭션 롤백: 예외가 발생했을 때 같은 트랜잭션 안의 변경을 취소하는 동작
- 런타임 예외: Spring 트랜잭션이 기본적으로 롤백 대상으로 보는 예외
- `noRollbackFor`: 특정 예외가 발생해도 트랜잭션을 롤백하지 않도록 지정하는 옵션

### 프로젝트 적용

- 결제 성공 API는 먼저 주문이 만료되었는지 확인한다.
- 만료된 주문이면 주문 상태를 `CANCELED`로 변경하고 재고를 복구한다.
- 이후 `ORDER_PAYMENT_EXPIRED` 실패 응답을 반환하되, 해당 예외는 `noRollbackFor`로 지정해 취소와 재고 복구를 커밋한다.

### 추가로 공부할 것

- checked exception과 unchecked exception의 롤백 차이
- 트랜잭션 전파 옵션
- 실패 응답을 반환하면서 보상 처리를 커밋하는 다른 설계 방식

## 성능 개선에 활용할 CS 개념

### 한 줄 정리

성능 개선은 특정 기술을 추가하는 일이 아니라, 병목을 측정한 뒤 동시성, 트랜잭션, 락, 인덱스, 배치 처리 같은 CS 개념으로 원인을 설명하고 개선하는 과정이다.

### 왜 필요했나

이 프로젝트의 목표는 CS 지식을 활용해 이커머스 주문 처리 성능을 개선하는 것이다.
주문 생성은 재고 차감, 쿠폰 예약, 주문 저장을 하나의 트랜잭션으로 처리하므로 단순 응답 시간뿐 아니라 정합성과 처리량을 함께 봐야 한다.

### 핵심 개념

- 동시성 제어: 여러 요청이 같은 재고나 쿠폰을 동시에 수정할 때 정합성을 유지하는 방법이다.
- 트랜잭션: 재고 차감, 쿠폰 예약, 주문 저장을 하나의 성공 또는 실패 단위로 묶는다.
- 비관적 락: 충돌 가능성이 높다고 보고 먼저 DB 행을 잠근 뒤 수정한다.
- 낙관적 락: 충돌이 드물다고 보고 수정 시점에 버전 충돌을 감지한다.
- 조건부 업데이트: `where quantity >= ?` 같은 조건으로 DB에서 검증과 수정을 원자적으로 처리한다.
- Critical section: 동시에 접근하면 안 되는 핵심 구간이며, 짧을수록 대기 시간이 줄어든다.
- 락 대기 시간: 같은 행을 수정하려는 트랜잭션이 앞 트랜잭션 종료를 기다리는 시간이다.
- 인덱스와 실행 계획: DB가 어떤 경로로 데이터를 찾는지 확인하고 조회 비용을 줄이는 방법이다.
- 배치 처리: 만료 주문처럼 여러 데이터를 주기적으로 처리할 때 한 번에 처리할 범위와 락 경합을 관리하는 방식이다.

### 프로젝트 적용

- 인기 상품 주문 생성은 `stocks` 행에 요청이 몰리는 hot row 문제로 볼 수 있다.
- 현재 구현은 재고 초과 판매를 막기 위해 비관적 락을 사용한다.
- 성능 개선 단계에서는 비관적 락, 조건부 업데이트, 트랜잭션 범위 축소를 비교한다.
- 쿠폰 포함 주문은 `issued_coupons` 행 락이 추가되므로 재고 락과 쿠폰 락의 영향을 분리해서 측정한다.
- 결제 대기 만료 처리는 사용자 요청과 동시에 같은 재고 행을 수정할 수 있으므로 배치 크기와 인덱스를 확인한다.
- 상품/주문 조회 성능은 N+1, projection, pagination, 인덱스 관점에서 별도 후보로 다룬다.

### 성능 개선에서 중요한 관점

- 정합성 기준과 성능 기준을 분리한다.
- 초과 판매 0건, 쿠폰 중복 사용 0건은 반드시 만족해야 한다.
- p95, p99 응답 시간과 처리량은 개선 전후 비교 지표로 사용한다.
- 로컬 측정 수치는 운영 성능 보장이 아니라 같은 환경에서의 상대적인 개선 근거로 사용한다.
- 여러 개선을 한 번에 적용하지 않고 하나씩 적용해 효과를 분리한다.

### 추가로 공부할 것

- PostgreSQL `select for update`와 MVCC
- lock timeout과 deadlock
- HikariCP 커넥션 풀 지표
- 부하 테스트에서 throughput, latency, percentile 해석
- keyset pagination

## 쿠폰 예약과 상태 전이

### 한 줄 정리

쿠폰 예약은 고객이 주문을 생성해 결제 대기 상태에 들어갔을 때, 해당 쿠폰을 다른 주문에서 사용할 수 없도록 미리 점유하는 방식이다.

### 왜 필요했나

고객 보유 쿠폰은 한 번만 사용할 수 있다.
주문 생성 시 쿠폰을 예약하지 않으면 결제 대기 중인 주문이 쿠폰을 사용하려는 동안 같은 쿠폰으로 다른 주문을 만들 수 있다.

### 핵심 개념

- 상태 전이: 쿠폰은 `AVAILABLE -> RESERVED -> USED` 또는 `AVAILABLE -> RESERVED -> AVAILABLE` 흐름을 가진다.
- 동시성 제어: 같은 쿠폰을 동시에 예약하지 못하도록 발급 쿠폰 행을 잠근다.
- 보상 처리: 결제 취소 또는 결제 대기 만료 시 예약 상태를 해제한다.
- 트랜잭션 원자성: 주문 저장, 재고 차감, 쿠폰 예약 중 하나라도 실패하면 전체를 롤백한다.

### 프로젝트 적용

- 주문 생성 시 요청된 `IssuedCoupon`을 비관적 락으로 조회한다.
- 쿠폰 소유자, 상태, 만료 시간, 타입, 적용 대상을 검증한다.
- 주문 생성 성공 시 쿠폰을 `RESERVED`로 변경하고 주문과 연결한다.
- 결제 성공 시 예약 쿠폰을 `USED`로 변경한다.
- 결제 취소 또는 결제 대기 만료 시 예약 쿠폰을 `AVAILABLE`로 되돌린다.

### 추가로 공부할 것

- 쿠폰 발급 중복 제어
- 쿠폰 만료 상태 자동 갱신 방식
- 주문 할인 이력 테이블 분리 시점

## 주문 금액 스냅샷

### 한 줄 정리

주문 금액 스냅샷은 주문 생성 시점의 상품 가격, 할인 금액, 최종 결제 금액을 주문에 저장해 이후 정책 변경과 관계없이 주문 이력을 보존하는 방식이다.

### 왜 필요했나

상품 즉시 할인은 운영자가 상품에 설정하는 자동 할인이라 적용 기간이나 금액이 나중에 바뀔 수 있다.
이미 생성된 주문의 금액이 조회 시점의 할인 정책으로 다시 계산되면 결제 금액과 주문 이력이 달라질 수 있다.

### 핵심 개념

- 스냅샷: 변경될 수 있는 값을 특정 시점의 결과로 저장하는 방식
- 할인 계산 순서: 상품 원금액에서 상품 즉시 할인, 특정 상품 쿠폰, 전체 상품 쿠폰 순서로 차감한다.
- 수량별 할인: 상품 1개당 할인 금액을 주문 수량만큼 합산한다.

### 프로젝트 적용

- 상품 즉시 할인은 활성 상태이고 적용 기간에 포함될 때만 주문 생성에 반영한다.
- 즉시 할인 금액은 상품 1개당 금액으로 계산하고, 주문 수량만큼 합산해 `OrderItem.instantDiscountAmount`에 저장한다.
- 주문 전체 즉시 할인 합계는 `Order.totalInstantDiscountAmount`에 저장한다.
- 특정 상품 쿠폰은 즉시 할인 적용 후 남은 상품 1개 금액까지만 적용한다.

### 추가로 공부할 것

- 주문 할인 이력 테이블 분리 시점
- 할인 정책 우선순위가 여러 개일 때의 계산 모델
- 정산 시스템에서 주문 스냅샷을 사용하는 이유

## 유니크 제약과 중복 발급 방지

### 한 줄 정리

유니크 제약은 특정 컬럼 조합의 중복 저장을 DB가 직접 막아주는 제약이고, 동시 요청에서도 데이터 정합성을 지키는 최종 방어선이 된다.

### 왜 필요했나

쿠폰은 고객당 같은 쿠폰 원본을 1번만 발급받을 수 있어야 한다.
서비스 코드에서 먼저 발급 이력을 확인하더라도 동시에 두 요청이 들어오면 둘 다 아직 발급되지 않았다고 판단할 수 있다.

### 핵심 개념

- 유니크 제약: 같은 컬럼 조합의 중복 행을 저장하지 못하게 하는 DB 제약
- 경쟁 조건: 여러 요청이 동시에 같은 데이터를 확인하고 수정하면서 기대와 다른 결과가 생기는 상황
- 방어적 검증: 애플리케이션에서 사용자에게 명확한 에러를 주고, DB에서 최종 정합성을 보장하는 방식

### 프로젝트 적용

- `issued_coupons` 테이블에 `(coupon_id, customer_id)` 유니크 제약을 추가했다.
- 쿠폰 발급 서비스는 먼저 기존 발급 여부를 확인해 `COUPON_ALREADY_ISSUED`를 반환한다.
- 동시에 발급 요청이 들어와 DB 제약에 걸리는 경우도 같은 비즈니스 에러로 처리한다.

### 추가로 공부할 것

- 트랜잭션 격리 수준
- unique index와 unique constraint 차이
- 동시 발급 요청을 재현하는 통합 테스트 방식

## React, Vite, JavaScript의 역할

### 한 줄 정리

JavaScript는 브라우저에서 실행되는 언어이고, React는 UI를 컴포넌트로 구성하는 라이브러리이며, Vite는 개발 서버와 정적 빌드를 담당하는 프론트엔드 개발 도구다.

### 왜 필요했나

백엔드 API는 이미 Spring Boot로 구현되어 있다.
포트폴리오용 웹 UI는 백엔드 기능을 실제 고객 흐름으로 사용할 수 있게 보여주는 클라이언트 역할을 하므로, 복잡한 풀스택 프레임워크보다 가벼운 React 앱이 적합하다고 판단했다.

### 핵심 개념

- JavaScript: 브라우저에서 UI 상호작용과 API 호출을 처리하는 언어
- React: 상품 카드, 장바구니, 주문 상세, 상태 패널 같은 UI를 컴포넌트 단위로 나누는 라이브러리
- Vite: 개발 중 빠른 dev server를 제공하고, 배포 시 HTML/CSS/JavaScript 정적 파일로 빌드하는 도구
- 정적 빌드: 개발용 소스 코드를 브라우저가 내려받아 실행할 수 있는 파일 묶음으로 만드는 과정
- SPA: 최초 로드 후 JavaScript가 API를 호출하고 화면을 갱신하는 단일 페이지 애플리케이션 방식

### 프로젝트 적용

- 프론트엔드는 React, Vite, JavaScript로 시작한다.
- 화면은 실서비스형 MVP UI로 구성하고, 백엔드 상태 변화는 보조 관찰 패널로 보여준다.
- 프론트엔드는 백엔드 API를 호출해 상품, 장바구니, 쿠폰, 주문 상태를 갱신한다.
- 배포 방식은 이후 결정하되, Vite 빌드 결과물은 정적 파일로 배포하거나 Spring Boot에서 함께 서빙할 수 있다.

### 추가로 공부할 것

- React Router
- CORS
- 정적 호스팅과 CDN
- Vite 빌드 결과물 구조
- TypeScript 도입 시점

## Vite 개발 서버와 API 프록시

### 한 줄 정리

Vite 프록시는 브라우저가 프론트엔드 서버(`/api`)로 보낸 요청을 개발 서버가 백엔드 서버로 대신 전달해주는 기능이다.

### 왜 필요했나

프론트엔드는 `http://localhost:5173`, 백엔드는 `http://localhost:8080`에서 실행된다.
브라우저 기준으로는 서로 다른 출처이기 때문에 직접 호출하면 CORS 정책을 고려해야 한다.
첫 프론트엔드 구현에서는 백엔드 보안 설정을 넓히지 않고 개발 환경에서만 프록시로 연결하기로 했다.

### 핵심 개념

- Origin: 프로토콜, 호스트, 포트 조합이다.
- CORS: 다른 Origin의 리소스를 브라우저가 호출할 때 서버가 허용 여부를 알려주는 보안 정책이다.
- Dev server proxy: 프론트엔드 개발 서버가 특정 경로 요청을 백엔드로 전달하는 개발 편의 기능이다.

### 프로젝트 적용

- 프론트엔드 Vite 앱은 `frontend/` 폴더에 둔다.
- Vite 설정에서 `/api` 요청을 `http://localhost:8080`으로 프록시한다.
- 프론트엔드 코드는 `/api/v1/products`처럼 백엔드 API 경로를 그대로 호출한다.

### 추가로 공부할 것

- 운영 배포에서 CORS를 설정하는 방식
- reverse proxy와 dev server proxy 차이
- 프론트엔드 정적 파일을 Spring Boot에서 서빙하는 방식

## Tailwind CSS와 디자인 토큰

### 한 줄 정리

Tailwind CSS는 미리 정의된 작은 utility class를 조합해 UI를 만드는 CSS 프레임워크이고, 디자인 토큰은 색상, 폰트, 간격, 그림자 같은 디자인 기준을 코드에서 일관되게 재사용하기 위한 값이다.

### 왜 필요했나

프론트엔드 화면이 상품, 장바구니, 쿠폰, 체크아웃, 주문, 상태 관찰 패널까지 늘어나면서 CSS가 복잡해졌다.
특히 좁은 화면에서 체크아웃 레이아웃이 겹치고, 쿠폰 화면과 상태 관찰 패널의 구분감이 부족했으며, `DESIGN.md`의 Pretendard 폰트와 RIDI 기반 색상 체계가 UI에 충분히 적용되지 않았다.

### 핵심 개념

- Utility-first CSS: `flex`, `gap-4`, `rounded-lg`, `text-sm`처럼 작은 클래스를 조합해 스타일을 만든다.
- 디자인 토큰: `ridi-blue`, `deep-charcoal`, `background-subtle`처럼 반복 사용할 디자인 값을 이름 붙여 관리한다.
- 반응형 유틸리티: 화면 크기별로 `sm:`, `md:`, `lg:` 같은 접두사를 사용해 레이아웃을 바꾼다.
- 컴포넌트 추출: 긴 class 조합이 반복되면 React 컴포넌트나 작은 스타일 헬퍼로 묶는다.

### 프로젝트 적용

- Tailwind CSS를 전체 프론트엔드 리팩토링 기준으로 도입한다.
- `DESIGN.md`의 Deep Charcoal, RIDI Blue, Pure White, Background Subtle, Pretendard 계열 폰트를 Tailwind 설정에 반영한다.
- 기본 CTA는 `DESIGN.md` 기준에 따라 차콜 계열을 우선하고, RIDI Blue는 정보성 강조, 활성 탭, 포커스, 보조 CTA에 사용한다.
- 체크아웃 화면은 좁은 화면에서 상품 정보와 쿠폰 선택이 세로로 쌓이도록 반응형 레이아웃을 정리한다.
- 쿠폰 화면은 발급 가능 쿠폰과 내 보유 쿠폰을 탭으로 분리한다.
- 상태 관찰 패널은 페이지 본문과 다른 배경, 경계선, 그림자로 구분한다.

### 추가로 공부할 것

- Tailwind configuration
- CSS reset과 Preflight
- 디자인 토큰 네이밍
- 반응형 레이아웃 설계
- Headless UI와 Radix UI

## 첫 주문 쿠폰 구현 시점

### 한 줄 정리

고객 생명주기와 연결된 쿠폰 정책은 고객 도메인과 인증 흐름이 준비된 뒤 구현해야 규칙과 동시성 제약을 명확하게 만들 수 있다.

### 왜 필요했나

첫 주문 쿠폰은 "첫 결제 완료 주문이 없는 고객"이라는 조건뿐 아니라 고객당 1회 발급, 주문 생성 시 예약, 결제 확정 시점 검증, 동시 요청 제어까지 함께 고려해야 한다.
현재 프로젝트에는 회원가입, 인증/인가, 고객 테이블이 아직 없으므로 이 정책을 현재 데모 쿠폰에 붙이면 구현 범위가 커지고 책임이 흐려진다.

### 핵심 개념

- 도메인 불변식은 적절한 소유 주체가 있을 때 가장 명확하게 표현된다.
- 첫 주문 쿠폰은 쿠폰 원본보다 고객 가입 이벤트와 보유 쿠폰 발급 이력에 더 강하게 묶인다.
- 동시성 제약은 단순 조회 후 저장보다 DB 제약, 고객 단위 락, 발급 이벤트 단일화처럼 강한 장치가 필요할 수 있다.

### 프로젝트 적용

- 현재 데모 데이터에서는 첫 주문 쿠폰을 제거하고 일반 전체 상품 쿠폰과 상품 쿠폰만 제공한다.
- 이후 인증/인가와 회원가입 기능을 구현하면, 회원가입 시 고객당 1개 첫 주문 쿠폰을 자동 발급하는 정책으로 다시 설계한다.
- 그 시점에는 중복 발급 방지, 만료 처리, 결제 완료 기준 첫 주문 판정, 동시 요청 제어를 함께 검토한다.

## 시드 데이터와 부모-자식 정합성

### 한 줄 정리

외래키가 있어도 자식 row가 "존재하는 부모"에 연결되는지만 보장할 뿐, "의도한 부모"에 연결되는지는 별도로 검증해야 한다.

### 왜 필요했나

데모 상품은 고정 ID로 insert된다.
기존 DB에 같은 ID의 다른 상품이 있으면 상품 insert는 건너뛰지만, 재고, 즉시 할인, 상품 쿠폰이 ID만 보고 그 기존 상품에 연결될 수 있었다.

### 프로젝트 적용

- 데모 자식 데이터는 상품 ID뿐 아니라 이름, 가격, 상태, 콘텐츠, 카테고리, 설명까지 일치하는 데모 상품 row에만 연결한다.
- 같은 ID의 다른 상품이 있는 DB에서는 데모 자식 데이터를 생성하지 않는다.
- Flyway 테스트로 ID 충돌 시 재고, 즉시 할인, 상품 쿠폰이 붙지 않는지 검증한다.

## Identity Sequence와 명시 ID Insert

### 한 줄 정리

DB identity 컬럼에 ID를 직접 넣는 것과 다음 자동 발급 ID를 관리하는 sequence가 전진하는 것은 별개의 문제다.

### 왜 필요했나

데모 상품은 `10001`부터 `10005`까지 고정 ID로 insert된다.
PostgreSQL에서 이 값들을 명시적으로 넣어도 자동 발급 sequence가 낮은 값에 남아 있으면, 이후 상품 등록 시 이미 존재하는 ID를 다시 발급할 수 있다.

### 프로젝트 적용

- 데모 상품 insert 이후 `products.id` identity를 현재 `max(id) + 1`로 재시작한다.
- PostgreSQL 전용 `setval` SQL 대신 Flyway Java migration을 사용해 PostgreSQL과 H2 테스트에서 같은 의도를 검증한다.
- 기존 DB에 데모 ID보다 큰 상품 ID가 있어도 자동 발급 ID가 그 이후로 이동하는지 테스트한다.
